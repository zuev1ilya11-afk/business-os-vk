# Финальный запуск Business OS на 139.100.237.167

`python3 finish_release.py --cutover` выполняется от root на российском сервере. Это **реальное переключение новой системы на запись**, не очередная репетиция. Пользователь согласовал паузу; сотрудники в этот период не меняют заявки и отчёты.

Сначала программа собирает статический интерфейс из проверенного main7e3fb71, использует35 уже проверенных eszip и точные локальные image ID успешной проверки. Поднимает Caddy2.11.7, получает доверенный IP-сертификат Let's Encrypt shortlived и проверяет HTTPS без `-k`. Сертификаты сохраняются в `/opt/business-os/data/https-certificates` и продлеваются Caddy автоматически. В этот момент источник ещё работает. Также заранее запускается новая пустая БД и проверяется доступ по приватной Docker-сети.

Затем терминал скрыто запрашивает пароль исходной PostgreSQL и серверный Storage API-ключ. Сохраняются точные исходные флаги, SQL восстановления и `resume-source.sh`. Отключаются исходные четыре задания cron и runtime-флаги, завершаются уже начатые отправки Hands/push, исходная БД переводится в readonly; обычные клиентские соединения переподключаются. Платформенные superuser-процессы не завершаются.

Создаётся свежий полный pg_dump, роли без паролей, Vault и инвентарь файлов. Дамп восстанавливается в новую `bos_restore_check`, сравниваются все выгруженные таблицы и счётчики, Vault переупаковывается проверенным алгоритмом. Все актуальные файлы скачиваются с проверкой MD5/размера, затем SHA256. Исторические подписанные ссылки переоформляются новым Storage; бизнес-поля, оплаты и пароли сотрудников не пересчитываются. Три URL фоновых обработчиков и database у cron переводятся на целевые адреса.

REST/Auth/Storage/Edge запускаются в отдельных пространствах сети на приватной Docker-сети. Только Caddy слушает публичные80/443; Edge доступен хосту на127.0.0.1:19000. SQL-порт не опубликован. API остаётся закрыт для клиентов до проверки входа на удаляемом временном сотруднике. Три одноразовых/тестовых функции закрыты. Доступ функций, требующих JWT, сохраняется. Авторизация и роли BOS остаются прежними.

Перед открытием API сохраняется `activation-attempted.json`. **С этого момента источник автоматически не размораживается**, даже если последующий шаг упадёт: в новой системе уже могли появиться записи. До этой границы ошибка останавливает созданные контейнеры и восстанавливает исходные флаги и запись. После открытия активируются исходные фоновые задания на новом сервере; старые остаются отключены.

Каждый запуск использует отдельный `/opt/business-os/deploy/release-*`. В нём: конфигурация, секреты0600, свежая копия, журнал, `control.sh status|start|stop`, `resume-source.sh` и итоговый `report.json`. Старые пробные контейнеры и рабочий `business-os-db` не изменяются. Не удалять каталог работающего выпуска, его Docker volume `<имя-db-контейнера>-config` с ключами БД и общие HTTPS-сертификаты. После активации возврат старого URL без обратной синхронизации данных запрещён.

Успех обозначается **BOS_RU_APP_ONLINE** с адресом https://139.100.237.167 и актуальными счётчиками. Этот маркер ещё не означает, что старый GitHub Pages/PWA/VK адрес переключён, что выполнен реальный вход в браузере, проверена доставка уведомлений или изменены внешние webhook URLs. Старый frontend будет перенаправлен отдельным минимальным изменением после подтверждения работы сервера. Supabase Cloud не удаляется и не ставится на паузу целиком. Автоматические/offsite backups и перенос установки PWA между origins этим скриптом не создаются.
