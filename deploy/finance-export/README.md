## Самостоятельный пакет

`build.py` создаёт воспроизводимый `bos-finance.pyz` без внешних Python-библиотек.
Внутри — проверенные before/after исходники приложения, SHA-256 manifest,
установщик, анализатор eszip и только синтетические данные для проверки Excel.
На сервере нужны Linux/root, Python 3, Docker, nsenter, systemd,
минимум 1 GiB доступной RAM и свободного диска. Для первоначальной сборки
нужен доступ к npm registry; исполняемый код установщика не докачивается.

Режимы:

```sh
python3 /tmp/bos-finance.pyz --check
python3 /tmp/bos-finance.pyz --prepare
python3 /tmp/bos-finance.pyz --apply
python3 /tmp/bos-finance.pyz --rollback
```

`--apply` сам выполняет подготовку, если её ещё нет. Сначала он:

1. Проверяет mounts, текущий manifest, API baseline, финансовые модели,
   опубликованные статические файлы и реальные названия колонок через
   `information_schema` в транзакции `READ ONLY`. Клиентские строки не читает.
2. Создаёт частную резервную копию и журнал в
   `/opt/business-os/deploy/finance-xlsx-480c3145`.
3. Из текущей eszip извлекает точные версии npm-зависимостей, формирует frozen
   lock и воспроизводит baseline тем же Docker image. Проверяет код, карты,
   dependency graph и opaque-секции; порядок сериализации несущественен.
4. Отключает сеть сборочного контейнера, компилирует финансовое дополнение,
   проверяет неизменность существующих зависимостей и границы новых модулей.
5. Готовит частную копию gateway: из `routes.json` оставляет только
   mini-app-api, сохраняя структуру маршрута и флаги. Строки проверяются
   по списку локальных путей этого API; неизвестные значения и файлы
   останавливают подготовку. Секреты report config заменяются вымышленными.
   Запускает реальный gateway и новую eszip в контейнере `--network=none`,
   с вымышленными ключами и REST-данными. Проверяет XLSX, итоговые суммы,
   owner/manager, запрет master/dispatcher, поддельные/истёкшие сессии,
   фильтр Hands, пустой период и stale revision. Любые записи mock REST запрещены.

Только после этих проверок установка приостанавливает существующий архивный
таймер, дожидается окончания его текущего задания и заменяет нужные файлы.
Edge API кратко перезапускается. Установщик повторно применяет существующий
`bos-google-route.service`, проверяет health и запрет анонимной выгрузки
внутри контейнера и по публичному HTTPS, затем обновляет web и проверяет
публичные хеши. Предыдущее активное/неактивное состояние таймера сохраняется.
Успех: `FINANCE_DEPLOYED=...`, `DATABASE_CHANGED=false`.

Сохраняются действующий RU-router, gateway, остальные API-бандлы, отчёты,
Google route/config, Docker configuration и все несвязанные web-файлы.
Меняются только mini-app-api и два новых изолированных модуля экспорта,
три существующих и два новых web-файла, а также маркеры/manifest версии.
Миграций и записей в production-БД нет; финансовые формулы не меняются.

Попытка пакета 58cc6eb остановилась до staging: SERVER_MODEL_DIFFERS_order-payroll.js.
Diff пользователя подтвердил, что API использует source-60-40-v1, а проверенный
интерфейс — company-share-v2. Никакие существующие модели API теперь не входят
в список допустимых записей. Новый finance-export-models.mjs содержит отдельные
CommonJS-обёртки неизменённых UI read models; они не читают и не заменяют
API globals. Повторная baseline-сборка и сравнение всех старых исполняемых
модулей по-прежнему обязательны. Расхождение зафиксировано в документации
функции, а не исправлено скрытой заменой старого серверного кода.

## Ошибки и восстановление

До активации любая несовместимость оставляет production без изменений.
Во время активации ошибка запускает guarded rollback: проверяются резервные
хеши и отсутствие чужих изменений, восстанавливаются исходные файлы и версия,
перезапускается API и возвращается состояние архивного таймера.
Ручной `--rollback` также ждёт завершения архивного задания.

При `SIGKILL` автоматический откат невозможен; сохранённый журнал позволяет
повторить `--rollback`. Создаваемые контейнеры заранее записываются в частный
журнал и помечаются меткой stage: повторный запуск удаляет только контейнеры
с совпадающими записью, именем и меткой. Чужие контейнеры не удаляются.
Если после установки появились сторонние изменения затронутых файлов,
откат останавливается до их перезаписи. Резервную папку нужно сохранять.

`FINANCE_STOPPED=...` — остановка, а не успешная установка. Полные локальные
логи лежат в частной папке stage/logs; не публиковать их целиком. В консоль
выводятся коды состояния, без токенов, строк клиентов и ответов сервисов.

## Проверки

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s deploy/finance-export -p 'test_*.py' -v
python3 deploy/finance-export/build.py
npm run build:check
```

28 локальных тестов покрывают диагностику, границы путей/схемы, eszip checksum
и dependency drift, установку/ручной откат на диске, частичную ошибку записи,
сохранение сторонних изменений, повреждение backup/candidate, занятый архивный
worker, оба состояния таймера и очистку только своих контейнеров. Дополнительные проверки gateway
подтверждают сохранность production-файлов, исключение чужих маршрутов и
секретов из тестовой копии, отказ при внешних URL/path escape и неизвестном JSON.
Реальная сборка закреплённым Docker image и gateway проверяются самим пакетом
на сервере до изменения production; локально они не считаются выполненными.

Функция выгрузки ранее прошла 819 server и 876 browser тестов. После изоляции
повторно прошли 821 server тест, три проверки изоляции (включая native ESM),
семь браузерных сценариев, Deno typecheck,
линтер новых модулей, build check и открытие примера XLSX в LibreOffice.
Подробное соответствие колонок данным и известные ограничения описаны в
`docs/finance-export/README.md`. Сверка реальных заявок требует проверки
в действующем интерфейсе после установки; синтетические тесты её не заменяют.

## Диагностический скрипт

`check.py` можно запускать отдельно. Он не изменяет файлы/БД и не перезапускает
контейнеры. `prepare-check.py` воспроизводит эталонные хеши и реальные
projections из проверенного commit. Runtime-модули активного bundle имеют
приоритет над устаревшими standalone-копиями. Нормализуются только три
известные базовые URL. Eszip хешируется потоково по 64 KiB с пределом 128 MiB,
отдельно от лимита исходников 4 MB. `CHECK_COMPLETE=true` означает окончание
диагностики и само по себе не означает установку.

## Результат запуска пакета 54f6d78 на сервере

Пользователь подтвердил успешное воспроизведение baseline и offline-сборку
кандидата. До запуска тестового контейнера проверка остановилась на

читает и передаёт `handleRelease` отдельно от JWT/VK секретов. Обработка этого
файла добавлена только для частной тестовой копии; рабочий gateway не меняется.
Фактическая совместимость формы маршрута и финальный runtime probe по-прежнему
проверяются на сервере до активации. Установка production ещё не подтверждена.

## Формат маршрута, подтверждённый на сервере

Пакет 7ac5d10 повторно прошёл baseline/offline-сборку и остановился до
изменений production на `GATEWAY_ROUTE_VALUE_UNSUPPORTED`. Полученная запись
`mini-app-api` содержит `entrypoint` = `supabase/functions/mini-app-api/index.ts`,
`import_map` = null, `verify_jwt` = false, `bundle_sha256` и словарь
`source_sha256`. В словаре перечислены `finance-expenses.js`, `order-payroll.js`,
`supabase/functions/_shared/hands-details.ts` и entrypoint.

Тестовая копия теперь принимает этот конкретный формат: хеши проверяются как
64 шестнадцатеричных символа, пути сверяются с перечисленным списком. Значения
сохраняются без пересчёта; остальные маршруты в тестовую копию не попадают.
Рабочий `routes.json` по-прежнему не входит в список изменяемых файлов.

Хеши в этой записи отличаются от текущих файлов, подтверждённых read-only
проверкой. Поэтому целостность определяется по фактическим исходникам и bundle,
с точным воспроизведением baseline, а не по метаданным `routes.json`. Изолированный
gateway должен пройти XLSX/права/фильтры с неизменёнными метаданными маршрута;
при несовместимости установка остановится до активации.

## Исправление адресов изолированного теста

Пакет d5146fb прошёл проверку маршрута и обе сборки, затем остановился на
`fixture-probe_FAILED` / `RUNTIME_STARTUP`. Журнал тестового контейнера показал
`invalid private upstream`: в новой конфигурации использовались имена
`bos-finance-probe-*`, которые существующий gateway не принимает.

Использованы те же `bos-release-probe-rest`, `bos-release-probe-auth` и
`bos-release-probe-storage`, что в проверенном `runtime-stage.py` исправления
отчётов (commit 800b057aebf19f9b837b29791f183fb7ad516263). Все три имени внутри
одноразового контейнера сопоставляются с `127.0.0.1:19001`; сохранены
`network=none`, проверка единственного интерфейса lo, тестовые ключи, заглушка
данных и read-only mounts из staging. Production env не копируется.
Добавлен тест реальной границы запуска: адреса и hosts согласованы, внешней сети
и опубликованных портов нет, рабочие секреты не попадают в команды.
