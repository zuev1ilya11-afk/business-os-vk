# Business OS — локальный пакет резервного копирования

`bos-backup.pyz` — один файл, Python 3.10+ и стандартная библиотека. Подготовлен для установленного выпуска `release-to2wblxf`, BUILD `f78221901b3b47887fa7`. Не является установщиком обновления или командой восстановления production.

## Что делает capture

1. Проверяет шесть работающих сервисов, BUILD, image manifest, закреплённые web/Edge mounts и маршруты REST/Auth/Storage в одну БД. Источники не угадываются. Дополнительно читает только mounts остальных, включая остановленные, контейнеров для защиты целевого пути.
2. Требует локальный файловый Storage с подтверждённым persistent mount, проверяет пути и свободное место. Не допускает symlink, hardlink, устройства/FIFO, вложенные Docker/host mounts или пересечение цели с рабочими источниками. Исключает сырые каталоги PostgreSQL.
3. Создаёт PostgreSQL custom dump и globals с ролями/правами, архивирует установленные файлы, конфигурацию и Storage, сохраняет **сами Docker-образы** через `image save`. Сохраняет полный Docker config в закрытом комплекте, без вывода его значений.
4. Проверяет exit codes, предупреждения, TOC дампа, состав/хеши файлов и image archive. Повторно проверяет источники и контейнеры; изменения останавливают capture. Только после проверки и синхронизации файлов публикует каталог комплекта.

Команды БД используют локальный socket, OS-user `postgres`, явные port/user/database и read-only PGOPTIONS. Унаследованные libpq service/адрес/credentials не используются. Таймаут действует и внутри `docker exec`, и для внешнего процесса. Доступ к socket должен уже работать без пароля; пакет не меняет настройки авторизации.

Файловые mounts БД проверяются по метаданным `config_file`, `hba_file`, `ident_file` и путям из `pg_file_settings`, а не по списку допустимых имён. Перед этим `data_directory` однозначно сопоставляется с persistent mount. Нестандартный source/target допустим только для конфигурационного пути, подтверждённого сервером вне PGDATA; произвольные SQL/данные и все DB directory mounts остаются исключены. Запрос выводит только пути внутри процесса пакета, без значений настроек или содержимого файлов. Это исправляет ограничение первоначального пакета, который мог остановиться с `DATABASE_FILE_MOUNT_UNSUPPORTED` из-за имени корректного конфига. Неизвестные файлы всё ещё останавливают проверку.

## Запуск готового файла

После получения и сверки файла из конкретного Git commit:

```sh
python3 /tmp/bos-backup.pyz capture
```

По умолчанию комплект сохраняется в `/root/bos-recovery/capture-…`. Родитель создаётся с правами `0700`, файлы — `0600`. Для другой заранее подготовленной цели доступен `capture --output /absolute/path`; она проходит ту же защиту от пересечения с mounts. Существующий неприватный каталог не исправляется молча — запуск остановится.

Для повторной проверки известного комплекта можно задать его полный путь в короткой shell-переменной `B`, затем:

```sh
python3 /tmp/bos-backup.pyz verify "$B"
```

`verify` ничего не извлекает, не загружает Docker-образы, не подключается к БД и не выполняет SQL. Отсутствующие, дополнительные, изменённые или небезопасные файлы приводят к отказу. Каталог `.partial` не принимается как завершённая копия.

## Состав и вывод

| Файл | Содержание |
| --- | --- |
| `database.dump` | Логический снимок одной подтверждённой БД, включая данные, схему и права |
| `globals.sql` | Глобальные объекты PostgreSQL, в том числе роли и password hashes |
| `files.tar` | Файлы mounts и конфигурации; оригинальные uid/gid/mode сохранены как метаданные |
| `images.tar` | Docker save выбранных image IDs |
| `private-config.json` | Приватные настройки контейнеров, источников, PostgreSQL extensions и образов |
| `inventory.json` | Состав файлового архива и хеши |
| `manifest.json` | Интервал capture, версия и контрольные суммы комплекта |

На экране — короткий JSON со статусами, без клиентов, секретов, содержимого env/SQL или сырого stderr. Успех процесса означает `capture=COMPLETE` и `integrity=VERIFIED`; он **не означает** готовность аварийного восстановления. SHA-256 подтверждает целостность относительно manifest, а не подлинность комплекта от неизвестного отправителя.

При ошибке выводится фиксированный код, exit status ненулевой. Частичный каталог остаётся приватным под именем `.capture-….partial`; он не заменяет существующие копии. Пакет не чистит старые копии и чужие файлы. Если файловая система отказывает во время финального rename/fsync, выдаётся `FINALIZE_DURABILITY_UNCONFIRMED`; при доступном rename каталог возвращается в partial. Такой запуск требует проверки места/носителя, а не объявления успеха.

## Границы результата

- Это **локальная онлайн-копия**, не независимая копия за пределами сервера. Комплект содержит реальные секреты и данные, не зашифрован; его нельзя прикладывать к issue, PR или чату. Передача во внешнее хранилище ещё не реализована.
- `pg_dump` даёт согласованный снимок одной БД. Globals и файловый Storage снимаются отдельно; повторная проверка файлов замечает изменения, но не устанавливает общую транзакционную точку. Поэтому `database_storage_consistency=NOT_PROVEN` всегда явно сохраняется. Обещаний RPO/RTO нет.
- `restore=NOT_RUN`, `independent_copy=NOT_VERIFIED`, `disaster_recovery_ready=false`. Эти статусы нельзя повысить редактированием manifest: `verify` их не принимает на веру.
- Пакет не перезапускает службы, не приостанавливает записи, не применяет SQL/миграции и не вызывает интеграции. Снятие дампа и чтение больших файлов/образов расходуют I/O и место; оценка свободного места консервативна, ошибки не скрываются.
- Восстановление настоящего комплекта требует отдельной изолированной среды, подходящих PostgreSQL extensions и проверки DB↔Storage, прав и приложения. Запуск архивных `.env`, `control.sh` или SQL на рабочей БД не входит в этот пакет. Постоянный стенд ещё не создан.

PostgreSQL описывает границы [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) и [pg_dumpall](https://www.postgresql.org/docs/17/app-pg-dumpall.html). Проверка архивов не заменяет реальное восстановление.

## Разработка и проверки

```sh
python3 -m unittest discover -s deploy/recovery
```

Для реальной PostgreSQL установить `BOS_RECOVERY_PG_BIN` в каталог бинарников PostgreSQL 17 и запустить:

```sh
python3 deploy/recovery/test_postgres.py --require
```

Интеграционная проверка создаёт только новые синтетические кластеры, делает настоящий dump и restore, проверяет роли/права/RLS, ограничения, триггеры и связь тестового файла с метаданными. Docker transport и images в этом тесте — явно обозначенные fixtures; это не восстановление production. Проверяется также отказ повреждённого реального дампа.

В CI PostgreSQL-тест выполняется в отдельном контейнере с `--network none`, без live mounts, с репозиторием read-only и временными данными в tmpfs. Локальная среда при запрете Unix sockets использует только loopback TCP; транспорт отмечается в тестовом выводе. Синтетический globals restore нормализует только единственную конфликтующую строку создания bootstrap-роли; захваченный архив не изменяется. Это устройство теста, не production-рецепт.

`python3 deploy/recovery/build.py` воспроизводит zipapp с фиксированными timestamps. CI проверяет его совпадение с исходниками. Пакет не включает тесты, сторонние зависимости или файлы данных.
