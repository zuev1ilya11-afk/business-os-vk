# Business OS — локальный пакет резервного копирования

`bos-backup.pyz` — один файл, Python 3.10+ и стандартная библиотека. Подготовлен для установленного выпуска `release-to2wblxf`, BUILD `f78221901b3b47887fa7`. Не является установщиком обновления или командой восстановления production.

## Что делает capture

1. Проверяет шесть работающих сервисов, BUILD, image manifest, закреплённые web/Edge mounts и маршруты REST/Auth/Storage в одну БД. Источники не угадываются. Дополнительно читает только mounts остальных, включая остановленные, контейнеров для защиты целевого пути.
2. Требует локальный файловый Storage с подтверждённым persistent mount, проверяет пути и свободное место. Не допускает symlink, hardlink, устройства/FIFO, вложенные Docker/host mounts или пересечение цели с рабочими источниками. Исключает сырые каталоги PostgreSQL.
3. Создаёт PostgreSQL custom dump и globals с ролями/правами, архивирует установленные файлы, конфигурацию и Storage, сохраняет **сами Docker-образы** через `image save`. Сохраняет полный Docker config в закрытом комплекте, без вывода его значений.
4. Проверяет exit codes, предупреждения, TOC дампа, состав/хеши файлов и image archive. Повторно проверяет источники и контейнеры; изменения останавливают capture. Только после проверки и синхронизации файлов публикует каталог комплекта.

Команды БД используют локальный socket, OS-user `postgres`, явные port/user/database и read-only PGOPTIONS. Унаследованные libpq service/адрес/options сбрасываются. `PGPASSWORD` и `PGPASSFILE`, уже заданные **внутри выбранного контейнера**, сохраняются для существующей аутентификации; пароль из окружения хоста туда не передаётся, значения не добавляются в argv или отчёт. Пакет не подставляет `POSTGRES_PASSWORD`, не меняет авторизацию и не запрашивает пароль в чате. Таймаут действует и внутри `docker exec`, и для внешнего процесса.

Для полной копии, включая password hashes в globals, нужен существующий административный доступ. Сначала read-only запрос проверяет роль `postgres`. Если она не superuser, пакет допускает ровно одну попытку подключения как уже существующий `supabase_admin`, только если каталог ролей подтвердил `LOGIN` и `SUPERUSER`. Новое соединение должно подтвердить свои `current_user`, `session_user`, ту же закреплённую БД и read-only режим. Выбранная роль используется для metadata, dump и globals и повторно проверяется в конце; её имя сохраняется только в приватной конфигурации. Нет `GRANT`, `ALTER ROLE`, создания ролей, смены паролей или перебора других учётных записей. Отсутствие подходящей роли либо отказ аутентификации останавливает запуск до создания каталога копии.

Файловые mounts БД проверяются по метаданным `config_file`, `hba_file`, `ident_file` и путям из `pg_file_settings`, а не по списку допустимых имён. Перед этим `data_directory` однозначно сопоставляется с persistent mount. Нестандартный source/target допустим только для конфигурационного пути, подтверждённого сервером вне PGDATA; произвольные SQL/данные и все DB directory mounts остаются исключены. Запрос выводит только пути внутри процесса пакета, без значений настроек или содержимого файлов. Это исправляет ограничение первоначального пакета, который мог остановиться с `DATABASE_FILE_MOUNT_UNSUPPORTED` из-за имени корректного конфига. Неизвестные файлы всё ещё останавливают проверку.

## Запуск готового файла

После получения и сверки файла из конкретного Git commit:

```sh
python3 /tmp/bos-backup.pyz capture
```

По умолчанию комплект сохраняется в `/root/bos-recovery/capture-…`. Родитель создаётся с правами `0700`, файлы — `0600`. Для другой заранее подготовленной цели доступен `capture --output /absolute/path`; она проходит ту же защиту от пересечения с mounts. Существующий неприватный каталог не исправляется молча — запуск остановится.

Для повторной проверки известного комплекта можно задать его полный путь в короткой shell-переменной `B`, затем:

```sh
python3 /tmp/bos-backup.pyz verify "$B"
```

`verify` ничего не извлекает, не загружает Docker-образы, не подключается к БД и не выполняет SQL. Отсутствующие, дополнительные, изменённые или небезопасные файлы приводят к отказу. Каталог `.partial` не принимается как завершённая копия.

Если capture успел записать весь комплект и manifest, но остановился при финальной проверке, исправленный пакет может завершить **последний** частичный комплект без нового dump или image save:

```sh
python3 /tmp/bos-backup.pyz finish-latest
```

Команда выбирает последнее имя `.capture-…partial` в том же приватном каталоге, заново проверяет все файлы, затем выполняет fsync и переименование. Она не подключается к Docker или БД, не переписывает время исходного capture, не перезаписывает готовые копии и не удаляет файлы. При неполном или повреждённом последнем комплекте останавливается; автоматического перехода к более старой копии нет. До успешного завершения `.partial` остаётся незавершённым. Для иной цели используется `finish-latest --output /absolute/path`.

## Состав и вывод

| Файл | Содержание |
| --- | --- |
| `database.dump` | Логический снимок одной подтверждённой БД, включая данные, схему и права |
| `globals.sql` | Глобальные объекты PostgreSQL, в том числе роли и password hashes |
| `files.tar` | Файлы mounts и конфигурации; оригинальные uid/gid/mode сохранены как метаданные |
| `images.tar` | Docker save выбранных image IDs |
| `private-config.json` | Приватные настройки контейнеров, источников, PostgreSQL extensions и образов |
| `inventory.json` | Состав файлового архива и хеши |
| `manifest.json` | Интервал capture, версия и контрольные суммы комплекта |

На экране — короткий JSON со статусами, без клиентов, секретов, содержимого env/SQL или сырого stderr. Успех процесса означает `capture=COMPLETE` и `integrity=VERIFIED`; он **не означает** готовность аварийного восстановления. SHA-256 подтверждает целостность относительно manifest, а не подлинность комплекта от неизвестного отправителя.

Проверка образов различает классический ID конфигурации и ID manifest/index в containerd image store. Для OCI проверяется связь закреплённого ID с нужной платформой, конфигурацией и всеми её слоями, включая digest и размер descriptor. Отсутствие другой платформы не подменяет наличие полной нужной платформы. Для классического архива проверяются config hash и слои из rootfs. Файлы архива читаются без извлечения или загрузки образов; ссылки и небезопасные пути не принимаются.

Для ошибок команды временно удерживается не более 8192 байт начала stderr в памяти, без записи в файл или вывода. Известные сообщения заменяются фиксированными кодами: `DATABASE_PASSWORD_REQUIRED`, `DATABASE_PASSWORD_REJECTED`, `DATABASE_METADATA_PERMISSION_DENIED`, `DATABASE_TIMEOUT_UNAVAILABLE`, `DATABASE_CLIENT_UNAVAILABLE`, `DATABASE_SOCKET_UNAVAILABLE` или `COMMAND_TIMEOUT`. Они сохраняются при проверке конфигов. Неизвестный текст скрывается за общим отказом. Недоступность `timeout` не включает неограниченный запуск, а отсутствие учётных данных не вызывает обход аутентификации.

При ошибке выводится фиксированный код, exit status ненулевой. Частичный каталог остаётся приватным под именем `.capture-….partial`; он не заменяет существующие копии. Пакет не чистит старые копии и чужие файлы. Если файловая система отказывает во время финального rename/fsync, выдаётся `FINALIZE_DURABILITY_UNCONFIRMED`; при доступном rename каталог возвращается в partial. Такой запуск требует проверки места/носителя, а не объявления успеха.

## Границы результата

- Это **локальная онлайн-копия**, не независимая копия за пределами сервера. Комплект содержит реальные секреты и данные, не зашифрован; его нельзя прикладывать к issue, PR или чату. Передача во внешнее хранилище ещё не реализована.
- `pg_dump` даёт согласованный снимок одной БД. Globals и файловый Storage снимаются отдельно; повторная проверка файлов замечает изменения, но не устанавливает общую транзакционную точку. Поэтому `database_storage_consistency=NOT_PROVEN` всегда явно сохраняется. Обещаний RPO/RTO нет.
- `restore=NOT_RUN`, `independent_copy=NOT_VERIFIED`, `disaster_recovery_ready=false`. Эти статусы нельзя повысить редактированием manifest: `verify` их не принимает на веру.
- Пакет не перезапускает службы, не приостанавливает записи, не применяет SQL/миграции и не вызывает интеграции. Снятие дампа и чтение больших файлов/образов расходуют I/O и место; оценка свободного места консервативна, ошибки не скрываются.
- Восстановление настоящего комплекта требует отдельной изолированной среды, подходящих PostgreSQL extensions и проверки DB↔Storage, прав и приложения. Запуск архивных `.env`, `control.sh` или SQL на рабочей БД не входит в этот пакет. Постоянный стенд ещё не создан.

PostgreSQL описывает границы [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) и [pg_dumpall](https://www.postgresql.org/docs/17/app-pg-dumpall.html). Проверка архивов не заменяет реальное восстановление.

## Разработка и проверки

```sh
python3 -m unittest discover -s deploy/recovery
```

Для реальной PostgreSQL установить `BOS_RECOVERY_PG_BIN` в каталог бинарников PostgreSQL 17 и запустить:

```sh
python3 deploy/recovery/test_postgres.py --require
```

Интеграционная проверка создаёт только новые синтетические кластеры, делает настоящий dump и restore, проверяет роли/права/RLS, ограничения, триггеры и связь тестового файла с метаданными. Docker transport и images в этом тесте — явно обозначенные fixtures; это не восстановление production. Проверяется также отказ повреждённого реального дампа.

Отдельный тест воспроизводит ограниченную роль `postgres`: metadata и globals от неё получают реальный отказ, существующий `supabase_admin` успешно создаёт полный комплект с хешами паролей. Роли и данные сравниваются до/после capture; дополнительно проверяется реальный SCRAM-отказ для кандидата с неверным паролем. Создание и изменение тестовых ролей выполняются только при подготовке синтетического кластера.

В CI PostgreSQL-тест выполняется в отдельном контейнере с `--network none`, без live mounts, с репозиторием read-only и временными данными в tmpfs. Локальная среда при запрете Unix sockets использует только loopback TCP; транспорт отмечается в тестовом выводе. Синтетический globals restore нормализует только единственную конфликтующую строку создания bootstrap-роли; захваченный архив не изменяется. Это устройство теста, не production-рецепт.

Отдельные CI jobs проверяют настоящий `docker image inspect` → `docker image save` → верификатор для classic и containerd image stores. Используются публичный PostgreSQL 17.6 и уникальный маленький синтетический образ; проверяются отдельные и совместный export по реальным image IDs. Демоны одноразовые, production не подключается, образы не запускаются и не загружаются из архива. Локальный запуск требует явных opt-in переменных из `test_docker.py`; `--require` запрещает молчаливый пропуск.

`python3 deploy/recovery/build.py` воспроизводит zipapp с фиксированными timestamps. CI проверяет его совпадение с исходниками. Пакет не включает тесты, сторонние зависимости или файлы данных.

## Пробное восстановление независимой копии

`bos-restore.pyz` — отдельный пакет для Python 3.12+ и локального Linux Docker Engine на amd64. Windows launcher `restore.ps1` использует установленный Python либо проверенный portable CPython 3.12.10 с python.org; системные PATH, политика PowerShell и production не изменяются. `restore.cmd` запускает его для `%USERPROFILE%\BOS-Backup`. Три файла запуска должны лежать **вне** каталога резервной копии. ZIP/runtime не содержат клиентских данных. Запускатель проверяет SHA-256 pyz, portable download и его распакованные файлы.

Drill повторно проверяет точные семь файлов и их SHA-256, image graphs и архивные пути. Принимается только локальный Docker endpoint; наличие установленных production-контейнеров останавливает запуск. Tagged image archives отвергаются, чтобы не перезаписать локальные теги; после `docker load` требуются исходные IDs, Config, RootFS и платформа. Переход между разными семантиками image store автоматически не угадывается.

Создаётся новый именованный том с уникальной меткой. Узкий init-helper копирует только три проверяемых файла внутрь тома. PostgreSQL запускается из точного сохранённого образа с новым `initdb`, с исходным именем bootstrap-роли, выведенным только из однозначных role grants дампа, отдельным временным администратором и только Unix socket, с минимальным профилем preload для захваченных extensions, без фоновых workers, сетей, опубликованных портов, исходных env/config/startup scripts. `psql ON_ERROR_STOP` восстанавливает globals; `pg_restore --create --exit-on-error` сохраняет database owner/ACL/settings. Ошибки не подавляются. Проверяются версия, extensions, guard отчёта и агрегатные количества без клиентских данных.

Файлы извлекаются в новый Linux-том, чтобы Windows не меняла регистр/семантику имён. Их повторный потоковый tar сравнивается с исходным inventory по составу, типу, размеру и SHA-256; на Windows распакованные секреты не записываются. После проверки исходные payloads хешируются снова. Свои контейнеры останавливаются/удаляются; новый том остаётся для дальнейшей проверки, существующие тома не переиспользуются. JSON-отчёт с агрегатами создаётся рядом с каталогом копии под новым именем.

Успех означает `DRILL_COMPLETED` в объёме `DATABASE_GLOBALS_AND_FILE_BYTES`. **Это ещё не закрытие M02:** application=NOT_RUN, storage_relationships=NOT_VERIFIED, xattrs=NOT_CAPTURED, database_storage_consistency=NOT_PROVEN, disaster_recovery_ready=false. Не запускать восстановленные интеграции или app с исходными ключами. Обычное логическое восстановление расширений не доказывает доступность расшифрованных Vault/TCE данных: исходные ключи отдельно не проверены.

`python3 deploy/recovery/build_drill.py` воспроизводит `bos-restore.pyz` и закрепляет его SHA-256 в launcher. CI проверяет два реальных Docker stores, dump→restore/ACL/RLS/guard/файлы на синтетической БД и отдельные Windows PowerShell 5.1 процессы для обоих Python-вариантов. Реальный клиентский комплект в CI не передаётся.

PostgreSQL 17 проверяет исходного grantor ролей: произвольная замена bootstrap-роли нарушает восстановление GRANTED BY. Пакет принимает только globals с единственным однозначным membership grantor и его canonical CREATE ROLE; лексер не принимает SQL внутри строк/комментариев за команды. Только соответствующий точный byte span CREATE ROLE удаляется из отдельной копии globals после проверки исходного SHA-256. Исходный архив, ALTER ROLE и все GRANTED BY сохраняются. Неоднозначность останавливается с DRILL_BOOTSTRAP_METADATA_REQUIRED; connection user не используется вместо доказательства. Это явно помеченный вывод из дампа, не ранее записанный source OID.

Права `GRANT ... ON PARAMETER` относятся к настройкам PostgreSQL, а не к членству в ролях. Канонические строки pg_dumpall распознаются отдельно, не участвуют в определении bootstrap-роли и полностью сохраняются при восстановлении. Регрессия включает операторский случай `GRANT SET ON PARAMETER log_min_messages TO supabase_realtime_admin;`; реальный Docker drill сверяет восстановленные parameter ACL и действие права SET. `REVOKE` пока не поддерживается и останавливает drill до Docker: реальный тест PostgreSQL 17.6 обнаружил, что начальный отзыв прав параметра без существующей записи ACL не сохраняет исходное ограничение владельца при последующей выдаче прав. Такой комплект не пропускается как проверенный.

Проверка файлов Windows различает path-stat и descriptor-stat: CPython 3.12 может возвращать creation time как ctime для пути и change time для открытого файла; executable bits также зависят от имени. Между API сравниваются device/file ID, тип, link count, размер, mtime и birthtime. Полные metadata сравниваются отдельно path-before/path-after и fd-before/fd-after; SHA-256, отказ links/reparse points и проверка реальных изменений сохранены. CI выполняет семь файловых проверок и полную валидацию синтетического комплекта на Windows под установленным и включённым portable Python.

Вспомогательные команды совместимы с GNU tools и BusyBox: SHA-256 вычисляется без GNU-only флагов и сравнивается только после проверки формата результата. Отсутствие утилиты, ошибка чтения/выполнения и неверный формат имеют отдельные коды; `DRILL_COPY_HASH_MISMATCH` означает только несовпадение вычисленного хеша. Подготовка globals не требует `dd status=none`, извлечение и повторное архивирование используют короткие флаги tar, извлечение выполняется от postgres с umask 077. Отдельный реальный тест BusyBox 1.37.0 воспроизводит отказ старой команды, проверяет полную подготовку файлов, SHA-256, отказ изменённых данных и извлечение/повторную проверку архива.


### Совместимость Supabase и диагностика v5

В исходном аудите release-БД наблюдались pg_cron и pg_net. Для их восстановления shared preload необходим; прежний пустой preload был несовместим. Пакет строит профиль только из захваченных имён extensions: pg_cron, pg_net, pg_stat_statements, pg_tle и pgaudit разрешены по фиксированному списку. cron.database_name совпадает с восстановляемой БД. Worker slots остаются 0, задания cron и hooks pg_tle отключены, сеть отсутствует. pgsodium/Vault не preloaded, поэтому внешний getkey script не вызывается. Произвольные конфигурация, environment и preload paths из исходного сервера не запускаются.

До globals/данных проверяются точная версия PostgreSQL, доступность захваченных версий extensions и совпадение default_version: обычный pg_dump не указывает VERSION при CREATE EXTENSION. Несовпадение останавливается отдельным кодом вместо незаметного обновления extension. После восстановления сверяются установленные версии, ожидаемый preload и отсутствие extension workers.

Ошибки запуска/globals/database сохраняются в новом приватном Docker-томе в /bos/database-startup.stderr.log, /bos/globals-restore.stderr.log и /bos/database-restore.stderr.log (0600). Эти журналы могут содержать SQL/данные: их нельзя публиковать целиком. На экран и в JSON выводятся только фиксированная категория, фаза и разрешённый SQLSTATE; путь к успешно записанному отчёту показывается и при отказе. Неизвестная причина остаётся SQL_RESTORE_FAILED, а полный журнал сохраняется для локального разбора.

После извлечения права только тестовой копии нормализуются: каталоги0700, файлы0600. BusyBox немедленно применяет режим каталогов при распаковке, поэтому каталоги архива без owner-rwx отвергаются до Docker-операций с FILE_DIRECTORY_MODE_UNSUPPORTED. Запись завершения извлечения проверяется отдельным маркером; преждевременный выход помощника не принимается за успех.

Дополнительный CI использует закреплённый digest публичного Supabase PostgreSQL17.11.0.017, настоящий pg_cron/pg_net и другие распространённые extensions. Полный синтетический dump→drill проверяет точные версии, роли/ACL/RLS/guard, байты файлов, неизменность источника, сохранение отключённых cron jobs и отсутствие extension workers. Это совместимость с семейством Supabase, а не утверждение о совпадении публичного образа с частным образом оператора. Результат смотреть по exact commit CI; исходный клиентский архив агенту недоступен.


## Локальное приложение после успешного restore

`bos-app.pyz` и `start-app.cmd` продолжают успешный drill. Приложенный операторский JSON связывает исходный том с точным manifest SHA256; отдельная рабочая копия получает только PGDATA и файлы. Повторного pg_restore нет. Контейнеры не получают доступ к исходному тому; новые службы используют свежие ключи, общий loopback namespace network-none и узкие subpath mounts. Архивная PostgreSQL конфигурация и role/database GUC заменяются только на рабочей копии, workers отключены. Роли и структура приложения остаются предметом проверки, production не подключается.

Windows портал связывает браузер со службами через bounded binary docker-exec/BusyBox nc, без Docker published ports. Отдельный Edge profile с запретом внешнего proxy-трафика, CSP и ранним преобразованием известных API/Storage URL предотвращает обращения к рабочему приложению. Стандартный браузер как fallback не запускается. Рабочий профиль, bundled Python и JSON остаются рядом с пакетом; распаковывать его на E:. Физическое расположение Docker VHD автоматически не доказывается и не меняется.

Storage objects сопоставляются с единственным ожидаемым архивным путём по захваченным настройкам. Все объекты должны реально выдаваться исходным Storage image с теми же размером/SHA256. Потерянные xattrs не объявляются восстановленными: для совпавших байтов локальная выдача может использовать MIME/encoding из БД. Исходный archive/baseline не меняются. Оператор затем проверяет вход, фото/акт и сквозной сценарий отчёта/финансов. LOCAL_SERVICES_READY не означает завершённой пользовательской проверки и не меняет disaster_recovery_ready=false.

После Ctrl+C удаляются только собственные контейнеры; исходный и рабочий тома сохраняются. Новый запуск создаёт новую рабочую копию, поэтому это проверка приложения, а не постоянный стенд M03. Инструкция владельцу — `APP-README.txt`. Реальные CI используют только синтетические данные; exact результаты фиксируются в VERIFICATION.json.
