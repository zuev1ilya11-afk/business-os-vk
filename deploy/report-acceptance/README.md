# Приём отчётов после смены адреса — 30.10.2026

Текущий статус (30.10.2026): приём отчётов установлен на production с отложенной
архивацией; пользователь подтвердил сохранение принятого отчёта. Worker timer
пока выключен. Подписанные GAS-проверки прошли на хосте и в network namespace
edge через адрес `142.251.143.142`; обычные DNS-адреса Googleusercontent дают
TCP timeout. Ниже сохранены описание исходной проблемы и этапы подготовки.

### Восстановление отправки через проверенный адрес Google

После `GOOGLE_ROUTE_READY=true` из `gas-route-check.py` запустить
`python3 /tmp/bos-send.py` (проверенную копию `google-route-install.py`).
Установщик использует уже находящиеся на сервере helpers `/tmp/bos-route.py`,
`/tmp/bos-activate.py` и их цепочку с проверкой SHA-256.

Он получает актуальные IPv4 `script.google.com`, проверяет кандидатов подписанными
запросами и лишь после успеха сохраняет резервные копии и добавляет оба имени
`script.google.com` / `script.googleusercontent.com` в hosts хоста и работающего
edge. Оба перехода используют один подтверждённый адрес. Ранее проверенный
`142.251.143.142` остаётся только последним кандидатом; без повторной успешной
проверки он не устанавливается. Диагностика показывает hostname, метод,
HTTP-статус и числовой код сетевой/TLS ошибки без URL, тела ответа или ключей. Docker hosts
записывается в тот же inode; контейнер и приложение не перезапускаются. Чужая
запись для этого имени или несовпадение image/mounts останавливают установку.
Проверка TLS, исходный URL и hostname сохраняются. Это адрес, проверенный для
текущего сетевого сбоя; его доступность в будущем не гарантируется.

Постоянный root oneshot `bos-google-route.service` восстанавливает принадлежащие
ему записи перед каждым запуском worker, в том числе после пересоздания hosts
Docker. Он требует тот же image и bind mounts, не хранит секреты и не использует
файлы `/tmp`. Config: `/etc/business-os/google-route.json`; helper:
`/opt/business-os/report-acceptance/google-route.py`. Связь с worker задаётся
отдельным drop-in; существующий service-файл не меняется.

После положительного ответа реальной `gas-bridge-health` вызывается проверенный
`activate.py --enable-archive` через его функцию активации. До этого момента
ошибка возвращает прежние hosts и файлы маршрута. Приём отчётов и БД не
откатываются. После запуска worker маршрут сохраняется для повторных отправок.
Приватный журнал и резервные копии находятся в `activate-*/google-route-*`.

`ARCHIVE_TIMER_ENABLED=true` подтверждает запуск расписания.
`REAL_ARCHIVE_DELIVERY_VERIFIED=true` отдельно подтверждает увеличение числа
завершённых заданий после первого запуска. `ARCHIVE_QUEUE` и `ARCHIVE_ERRORS`
показывают очередь и только безопасные коды ошибок; пустая очередь или статус
failed не считаются доказательством отправки. Исторические заявки не добавляются
в очередь этой операцией.

### Подготовка на подтверждённом RU-хосте

`stage.py` загружает только файлы проверенной версии
`8f1bb32b624c92d07a86dafe2c3196eb29da9903` и проверяет их SHA-256. Скрипт
поддерживает как `sources/<function>/index.ts`, так и вложенную структуру
`sources/<function>/supabase/functions/<function>/index.ts`, сохраняя относительные
импорты. Команда: `python3 stage.py --backup "$BOS_BAK"`.

Нужна уже созданная резервная копия `db.dump`, `db-list.txt`, `app.tar.gz`.
Скрипт сохраняет дополнительную копию live web/edge, приватную конфигурацию
контейнеров и найденные конфигурационные файлы. Затем проверяет исходники,
согласованность web manifest и воспроизводимость текущих eszip в том же образе
runtime. Исправленные функции собираются с тем же кешем зависимостей после
отключения сети. Логи и конфигурация остаются в приватном каталоге на сервере.

`STAGE_READY=true` означает только готовность скомпилированных кандидатов.
Миграция БД, обновление runtime env/GAS, проверка запросов и активация остаются
отдельными шагами. Скрипт не заменяет production-файлы, не запускает функции
приложения, не обращается к БД и не включает worker timer. При расхождении
выводит `STAGE_STOPPED` и сохраняет имеющиеся материалы подготовки.

Проверка самого staging-скрипта без Docker/сети:
`python3 -m unittest discover -s deploy/report-acceptance -p 'test_stage.py' -v`.

При `BUNDLE_BASELINE_DIFFERS_order-lifecycle-api` использовать `bundle-diff.py`.
Он читает уже сохранённые рабочую и пересобранную eszip, показывает совпадение
кода, путей модулей, графа npm, sourcemaps и дополнительного содержимого.
Отдельно проверяет, сводятся ли серверные изменения report-модулей клиента к
URL. Скрипт не меняет критерий допуска выкладки и не запускает сборку/приложение.
Ему нужен исходный `/tmp/bos-stage.py` с проверяемым SHA-256; результат остаётся
в приватном каталоге staging. Все тесты helpers:
`python3 -m unittest discover -s deploy/report-acceptance -p 'test*.py' -v`.

После подтверждённого npm drift (`2.117.3` → `2.118.0`) продолжение выполняет
`resume-stage.py`. Он использует сохранённый stage и проверенные `/tmp/bos-stage.py`
и `/tmp/bos-diff.py`, извлекает точные версии всего npm-графа из каждой рабочей
eszip, получает integrity соответствующих версий и создаёт отдельные frozen
lockfiles. Исходные import specifiers не переписываются. Повторная исходная
сборка должна совпасть по каждому модулю, sourcemap, redirects, npm-графу и opaque
данным; допускается только другой порядок сериализации записей. Исправления
собираются в том же builder после отключения сети.

В отдельном web-кандидате сохраняются RU-router/config, URL и пользовательские
правки старых helper-функций фото/акта. Меняются только проверенные участки
report-модулей, две согласованные правки карточки мастера и метаданные сборки.
Конфликт в интерфейсе не блокирует независимую подготовку backend, но выводит
`FRONTEND_READY=false`; такая подготовка не считается полным кандидатом.
`BACKEND_READY=true` и `FRONTEND_READY=true` ещё не означают активацию: остаются
миграция, runtime env, GAS/worker и изолированные/публичные проверки.

После добавления `../_shared/report-storage.ts` bundler может поднять общий
корень eszip: например, `drive-archive-api/index.ts` становится
`bos-src/drive-archive-api/index.ts`, когда корень архива — `/`.
В последнем случае начальный `/` сохраняется при разрешении путей; этот
вариант воспроизведён тестом по хешам ключей из серверной диагностики.
Проверка исправленного кандидата разрешает ключи относительно подтверждённого
исходного пути `/bos-src/...` и сравнивает реальные модули. Разрешены изменение
кода только входной функции и добавление именно её `report-storage.ts`;
остальные исполняемые модули, redirects и npm-граф остаются проверяемыми.

После двух `*_READY=true` запустить `verify-stage.py`. Он выбирает последний
готовый `locked-*/journal.json`, сверяет live/candidate и определяет активную БД
по реальному маршруту edge → REST → DB. В production выполняется только
read-only транзакция для списка имён ролей и расширений; пароли не читаются.
Резервная копия восстанавливается в новый контейнер того же image digest,
без сети, host ports и mounts рабочей БД, с выключенным запуском pg_cron.
Сервер PostgreSQL работает от пользователя postgres; root используется только
клиентом pg_restore для чтения backup 0600 через read-only bind. Данные контейнера
временные; контейнер и его собственные volumes удаляются в finally.
Миграция применяется дважды, затем проверяются принятие → очередь → ошибка →
повтор → подтверждение, блокировка старой lease и права RPC на восстановленной
схеме. Вывод содержит только статусы, origins отчётных файлов и фрагмент gateway
со скрытыми значениями строк. Полные логи остаются приватными на сервере.
`DB_VERIFICATION_READY=true` подтверждает только эту проверку; runtime env,
GAS deployment, запуск исправленного edge и активация ещё не выполнены.

После успешной проверки БД `runtime-stage.py` готовит отдельный `runtime-*`.
Он оборачивает ровно одно наблюдавшееся выражение `envVars:[...env,[...,slug]]`
в шлюзе, сохраняя существующий список ключей и весь routing. Только семь
обновляемых функций получают внутренний `http://127.0.0.1:9000`, публичный домен
и подтверждённые origins старых отчётов. Новый worker key доступен только
`drive-archive-api`; существующие service/VK/Hands/sync ключи сохраняются.
Конфигурация записывается в новый `bos-report-env.json` с правами 0600.

Скомпилированные функции проверяются в disposable edge того же image digest,
без внешней сети, host ports и production env. Локальный HTTP fixture проверяет
service JWT, читает искусственные акты/фото и имитирует REST/Storage/GAS.
Проверяются авторизация, CORS, принятие без вызова архива, повтор принятия,
машинная архивация, сохранение receipt и пустая очередь. `runtime-probe.py`
загружается из deploy-ветки только при совпадении встроенного SHA-256.
`RUNTIME_READY=true` означает готовность runtime-кандидата, но не публикацию.
GAS deployment отдельно не подтверждён; таймер архивации не включается до
обновления существующего Google Apps Script и проверки его версии.

При остановке runtime-проверка выводит HTTP-статус, краткую очищенную ошибку,
маршруты обращений к fixture и счётчики изменений искусственных данных.
Заголовки, токены и production-логи не выводятся. HTTP fixture поддерживает
как Content-Length, так и chunked framing потоковых запросов шлюза.

### Активация проверенного кандидата

`activate.py` использует точную проверенную версию `/tmp/bos-r2.py` и последний
успешный `runtime-journal.json`. Перед изменениями сверяет все хеши, реальные
bind mounts, маршрут БД и опубликованный web build. Два подписанных запроса
без вложений проверяют GAS: ошибочная подпись номера должна дать
`INVALID_ORDER_NUMBER_SIGNATURE`, правильная — `ACT_REQUIRED`. Это отличает
обновлённый обработчик от старого и не создаёт папки/файлы на Google Drive.
Отдельно через внутренний Storage читаются первые 16 байтов сохранённых акта
и фото последнего отчёта; signed URL и содержимое в консоль не выводятся.

После свежего `pg_dump` применяется только проверенная additive-миграция в
одной транзакции с ограничением ожидания блокировок. Контейнер edge кратко
останавливается для замены проверенных файлов; PostgreSQL, Storage, Auth,
REST и Caddy не перезапускаются. Bind roots сохраняются. Запись каждого файла
атомарная, прежние байты/права/владельцы остаются в приватном журнале установки.
Затем проверяются local/public health, REST с service JWT, отсутствие доступа
без сессии, CORS push, GAS, новая web-сборка и права очереди. Только после этого
устанавливается и запускается один проход systemd worker, затем таймер.

Успех: `PRODUCTION_UPDATED=true`, `ARCHIVE_TIMER_ENABLED=true`,
`GAS_DEPLOYMENT_VERIFIED=true`. Сбой после начала замены автоматически
останавливает worker и возвращает прежние файлы. Очередь и данные БД не
откатываются из старой копии; сохранённые решения не теряются. Для прерванного
процесса предусмотрен `python3 /tmp/bos-activate.py --rollback` с проверкой
конкурентных изменений файлов. При `ROLLBACK_REQUIRES_ATTENTION=true` сначала
разобрать приватный журнал, не повторять замену вслепую.

Проверка реальной доставки push на телефон и приём конкретного отчёта в
браузере остаются пользовательской проверкой после активации. Скрипт не
принимает существующие отчёты от имени сотрудника и не создаёт тестовые заявки.

При `GAS_CONNECTION_FAILED` до `ACTIVATION_DIR` production ещё не менялся.
`gas-check.py` отдельно читает текущие DNS-ответы, выполняет TLS HEAD-проверки
обоих Google-хостов по IPv4/IPv6 и повторяет подписанную проверку без вложений.
Каждый HTTPS-переход показывает только hostname, метод, HTTP-статус, класс
ошибки и числовой errno/код сертификата. URL перенаправления, параметры,
ключи и тексты ответов не выводятся. Сертификаты проверяются, proxy не
подставляется, конфигурация сети и production не меняются. Используется
установленный `/tmp/bos-activate.py` с точным SHA-256 первой версии установщика.

## Что установлено

Исходная цепочка: `submitReportReview` в `order-lifecycle-v106.js` →
`order-lifecycle-api/reviewReport` → `archiveBeforeApproval` →
`${SUPABASE_URL}/functions/v1/drive-archive-api` → чтение сохранённых signed URL →
Google Apps Script → подтверждение Drive → UPDATE заявки.

Код держал решение проверяющего до успешной архивации. Вызов архивации имел
75-секундное ожидание, сама архивация — общий сетевой бюджет 60 секунд. Ошибка
из задания формируется именно в этой цепочке. Браузерный polling для принятия
не используется: увеличение его ожидания не решило бы проблему.

Дополнительные подтверждённые проблемы исходников:

- URL вложения сравнивался с origin `SUPABASE_URL`. Внутренний Docker URL и
  публичный HTTPS URL после переезда могут различаться. Archiver скачивал сам
  старый публичный URL, вместо обращения к внутреннему хранилищу.
- В исходниках клиента оставались адреса облачного Supabase/AppDeploy/Netlify;
  на сервер раньше ставился отдельный RU-router. Стандартная сборка main его
  не содержит. Нужна сверка с текущей серверной сборкой, а не замена её вслепую.
- В CORS push-api отсутствовал `https://homemaster.qd.je`.
- Старый GAS удалял существующий файл перед загрузкой нового; отсутствовал lock.
- `supabase/{push,hands-report,avito-assistant}-activation.sql` содержат старые
  облачные адреса worker. Это **не доказательство**, что такие адреса сейчас в БД.

Точная причина сетевого таймаута на production не установлена: SSH и логи
не были доступны, запрос к домену из среды проверки получил HTML «Site Unavailable».
Нельзя по этому ответу заключать, что сайт недоступен всем пользователям.

## Новая цепочка

Один UPDATE сохраняет решение, текущий статус заявки, время, имя и ID проверяющего,
комментарий. AFTER-trigger в той же транзакции создаёт приватное задание архивации.
Сбой записи очереди откатывает транзакцию, потери задания при перезапуске нет.
Повтор решения возвращает сохранённую запись. CAS защищает новую версию отчёта и
изменённую заявку. Отклонение требует комментарий также на сервере.

Очередь: `pending → processing → completed/failed`; автоматические повторы с
задержкой до часа. Lease на 10 минут, защита старого worker по lease и версии
отчёта. Идентификатор версии содержит заявку, upload token и дату загрузки.
Завершение архивации не меняет решение, статус заявки, выплаты или уведомления.
В `orders.drive_archive_status` значение `archived` сохранено для совместимости;
оно соответствует `completed` в очереди. Таблица очереди закрыта от anon/authenticated.

Worker запускается раз в минуту systemd timer, обрабатывает одно задание. Ключ
машинного вызова отделён от пользовательской авторизации. Запросы файлов идут
на внутренний Storage с service-role авторизацией, только по проверенному пути
точной заявки/версии. Redirect при скачивании запрещён; лимиты размера сохранены.
Истёкшая signed-ссылка не мешает архивированию, пока исходный объект существует.

GAS использует lock и отдельную папку версии отчёта, повтор использует существующие
файлы. Предыдущие файлы не удаляются. Требуется обновление **действующего deployment
Google Apps Script**, а не только сохранение текста в редакторе.

Клиент после успеха показывает сохранённую сервером запись и сообщение об архиве.
При потере ответа сначала перечитывает данные, не повторяя запись автоматически.
Фото, оригиналы и акты известных прежних хостов нормализуются на текущий origin;
чужие сайты и Google Drive не переписываются. Старые URL в БД массово не меняются.

## Проверенные области и ограничения

| Область | Результат |
|---|---|
| Приём/отклонение, роли, повтор, потеря ответа, сохранённые выплаты | Серверные и браузерные регрессии |
| Очередь и SQL-триггер | Реальная тестовая PostgreSQL через PGlite; транзакции, leases, права, повторы |
| Storage / фото / акты / оригиналы | Allowlist и внутреннее скачивание; браузер на имитируемом HTTPS-origin |
| Новый origin | Same-origin router для Functions/Storage/Auth/REST/Realtime путей fetch |
| PWA | Пересобраны bundle, manifest, shell, BUILD_ID; существующий механизм обновления без очистки данных |

| Уведомление о принятии | Отдельного события report_approved в исходной push-схеме нет. Не объявляется реализованным |

## До публикации

1. Запустить `preflight.py` на рабочем Docker-хосте. Он только читает конфигурацию,
   печатает origins/порты/mounts и признаки наличия ключей, без значений секретов.
2. Сохранить backup БД, текущих функций, web-root, proxy/compose/env и версию GAS.
   Сверить current build и SHA с серверными исправлениями 28 октября.
3. Поднять отдельные БД/Storage/worker и GAS тестовую папку; не использовать реальные
   подписки push, Hands или Avito для тестовой отправки. Проверить на том же proxy.
4. Убедиться, что `drive_archive_status` допускает `processing` и `failed` в текущей
   схеме; проверить существующие triggers, UUID staff.id и маршрут authenticated Storage.
5. В тестовом окружении применить миграцию, обновить GAS, функции и env, запустить
   worker; затем обновить клиент. Проверить файл и повтор на реальном Google Drive.
6. Только после этого согласовать production release. Автоматической выкладки нет.

Нельзя запускать старые release-инсталляторы поверх текущей версии или весь `main`
вместо проверенного набора изменений: это может затереть серверные исправления.

## Откат

### Установка при недоступном Google Drive

Если `script.google.com` отвечает, но соединение с адресом ответа
`script.googleusercontent.com` не устанавливается, исправление принятия можно
включить отдельно от архивации:

```sh
python3 /tmp/bos-activate.py --defer-archive
```

Этот режим требует того же проверенного runtime-кандидата, сверяет все файлы,
проверяет чтение сохранённых вложений, создаёт свежую резервную копию БД и
применяет ту же миграцию. HTTP-проверки приложения, прав доступа, REST, CORS,
публичной сборки и схемы остаются обязательными. Проверка живого Google
отложена явно: установщик не считает её пройденной и не запускает worker.
Таймер установлен, выключен и отключён от автозапуска; отчёты остаются в
Storage, задания архивации — в БД. Принятие отчёта не ждёт Google Drive.

Успех этого режима:

```text
GAS_DEPLOYMENT_VERIFIED=false
ARCHIVE_TIMER_ENABLED=false
ARCHIVE_DEFERRED=true
PRODUCTION_UPDATED=true
```

После восстановления сетевого доступа:

```sh
python3 /tmp/bos-activate.py --enable-archive
```

Включение сверяет установленную версию, проверяет подписи/версию GAS и живой
маршрут из edge, затем запускает worker и таймер. Не переустанавливает код и
не применяет миграцию повторно. При сетевой ошибке приложение продолжает
работать, архивация остаётся отложенной. Если прервался запуск worker,
повтор команды сначала останавливает таймер. Повтор обычной установки при
отложенном архиве только показывает текущий статус и не включает отправку.
Без `--defer-archive` исходная обязательная проверка GAS сохранена.

### Восстановление файлов

```sh
systemctl disable --now bos-drive-archive.timer
```
```sh
systemctl stop bos-drive-archive.service
```

Восстановить **собственную резервную копию этой выкладки** функций, web-root и env,
сначала сверив, что после неё никто не публиковал другой релиз. Конкретные команды
копирования будут зависеть от inventory и каталога backup. Сохранить новый GAS:
он совместим со старой подписью и не удаляет файлы. Не откатывать БД целиком,
не удалять очередь/столбец ID проверяющего и не отменять принятые отчёты: миграция
аддитивная. Накопленная очередь останется до восстановления worker. После отката
повторить проверки входа, отчётов и текущего build.
