# Приём отчётов после смены адреса — 30.10.2026

Статус: исправление исходников и локальные проверки; на production не установлено.
Полная готовность требует проверки реальной конфигурации сервера и тестовой выкладки.

### Подготовка на подтверждённом RU-хосте

`stage.py` загружает только файлы проверенной версии
`8f1bb32b624c92d07a86dafe2c3196eb29da9903` и проверяет их SHA-256. Скрипт
поддерживает как `sources/<function>/index.ts`, так и вложенную структуру
`sources/<function>/supabase/functions/<function>/index.ts`, сохраняя относительные
импорты. Команда: `python3 stage.py --backup "$BOS_BAK"`.

Нужна уже созданная резервная копия `db.dump`, `db-list.txt`, `app.tar.gz`.
Скрипт сохраняет дополнительную копию live web/edge, приватную конфигурацию
контейнеров и найденные конфигурационные файлы. Затем проверяет исходники,
согласованность web manifest и воспроизводимость текущих eszip в том же образе
runtime. Исправленные функции собираются с тем же кешем зависимостей после
отключения сети. Логи и конфигурация остаются в приватном каталоге на сервере.

`STAGE_READY=true` означает только готовность скомпилированных кандидатов.
Миграция БД, обновление runtime env/GAS, проверка запросов и активация остаются
отдельными шагами. Скрипт не заменяет production-файлы, не запускает функции
приложения, не обращается к БД и не включает worker timer. При расхождении
выводит `STAGE_STOPPED` и сохраняет имеющиеся материалы подготовки.

Проверка самого staging-скрипта без Docker/сети:
`python3 -m unittest discover -s deploy/report-acceptance -p 'test_stage.py' -v`.

## Что установлено

Исходная цепочка: `submitReportReview` в `order-lifecycle-v106.js` →
`order-lifecycle-api/reviewReport` → `archiveBeforeApproval` →
`${SUPABASE_URL}/functions/v1/drive-archive-api` → чтение сохранённых signed URL →
Google Apps Script → подтверждение Drive → UPDATE заявки.

Код держал решение проверяющего до успешной архивации. Вызов архивации имел
75-секундное ожидание, сама архивация — общий сетевой бюджет 60 секунд. Ошибка
из задания формируется именно в этой цепочке. Браузерный polling для принятия
не используется: увеличение его ожидания не решило бы проблему.

Дополнительные подтверждённые проблемы исходников:

- URL вложения сравнивался с origin `SUPABASE_URL`. Внутренний Docker URL и
  публичный HTTPS URL после переезда могут различаться. Archiver скачивал сам
  старый публичный URL, вместо обращения к внутреннему хранилищу.
- В исходниках клиента оставались адреса облачного Supabase/AppDeploy/Netlify;
  на сервер раньше ставился отдельный RU-router. Стандартная сборка main его
  не содержит. Нужна сверка с текущей серверной сборкой, а не замена её вслепую.
- В CORS push-api отсутствовал `https://homemaster.qd.je`.
- Старый GAS удалял существующий файл перед загрузкой нового; отсутствовал lock.
- `supabase/{push,hands-report,avito-assistant}-activation.sql` содержат старые
  облачные адреса worker. Это **не доказательство**, что такие адреса сейчас в БД.

Точная причина сетевого таймаута на production не установлена: SSH и логи
не были доступны, запрос к домену из среды проверки получил HTML «Site Unavailable».
Нельзя по этому ответу заключать, что сайт недоступен всем пользователям.

## Новая цепочка

Один UPDATE сохраняет решение, текущий статус заявки, время, имя и ID проверяющего,
комментарий. AFTER-trigger в той же транзакции создаёт приватное задание архивации.
Сбой записи очереди откатывает транзакцию, потери задания при перезапуске нет.
Повтор решения возвращает сохранённую запись. CAS защищает новую версию отчёта и
изменённую заявку. Отклонение требует комментарий также на сервере.

Очередь: `pending → processing → completed/failed`; автоматические повторы с
задержкой до часа. Lease на 10 минут, защита старого worker по lease и версии
отчёта. Идентификатор версии содержит заявку, upload token и дату загрузки.
Завершение архивации не меняет решение, статус заявки, выплаты или уведомления.
В `orders.drive_archive_status` значение `archived` сохранено для совместимости;
оно соответствует `completed` в очереди. Таблица очереди закрыта от anon/authenticated.

Worker запускается раз в минуту systemd timer, обрабатывает одно задание. Ключ
машинного вызова отделён от пользовательской авторизации. Запросы файлов идут
на внутренний Storage с service-role авторизацией, только по проверенному пути
точной заявки/версии. Redirect при скачивании запрещён; лимиты размера сохранены.
Истёкшая signed-ссылка не мешает архивированию, пока исходный объект существует.

GAS использует lock и отдельную папку версии отчёта, повтор использует существующие
файлы. Предыдущие файлы не удаляются. Требуется обновление **действующего deployment
Google Apps Script**, а не только сохранение текста в редакторе.

Клиент после успеха показывает сохранённую сервером запись и сообщение об архиве.
При потере ответа сначала перечитывает данные, не повторяя запись автоматически.
Фото, оригиналы и акты известных прежних хостов нормализуются на текущий origin;
чужие сайты и Google Drive не переписываются. Старые URL в БД массово не меняются.

## Настройки релиза

На рабочем сервере настройки **не изменены**. Для Edge runtime:

| Переменная | Значение |
|---|---|
| `SUPABASE_URL` | Проверенный внутренний gateway, доступный из контейнера; сохранить внутренний маршрут |
| `BOS_PUBLIC_URL` | `https://homemaster.qd.je` |
| `BOS_LEGACY_STORAGE_ORIGINS` | Точные origins реально сохранённых URL, через запятую; включая старый порт, если он был |
| `BOS_DRIVE_GAS_URL` | URL обновлённого GAS deployment |
| `BOS_DRIVE_WORKER_KEY` | Новый случайный секрет минимум 32 символа; тот же в защищённом env systemd |
| `BOS_SYNC_KEY`, `VK_APP_SECRET`, `SUPABASE_SERVICE_ROLE_KEY` | Сохранить существующие, не выводить в журнал/чат |

На хосте systemd: `BOS_DRIVE_WORKER_URL` — проверенный локальный маршрут к
`/functions/v1/drive-archive-api` или текущий HTTPS-домен. Пример env рядом.
Proxy должен передавать `X-BOS-Drive-Worker`, существующие BOS auth headers,
маршруты `/functions/v1`, `/storage/v1`, `/auth/v1`, `/rest/v1`, `/realtime/v1`.
Проверить HTTPS, Forwarded headers, upload limits и WebSocket upgrade на месте.
Таймауты принятия отчёта не увеличивались.

## До публикации

1. Запустить `preflight.py` на рабочем Docker-хосте. Он только читает конфигурацию,
   печатает origins/порты/mounts и признаки наличия ключей, без значений секретов.
2. Сохранить backup БД, текущих функций, web-root, proxy/compose/env и версию GAS.
   Сверить current build и SHA с серверными исправлениями 28 октября.
3. Поднять отдельные БД/Storage/worker и GAS тестовую папку; не использовать реальные
   подписки push, Hands или Avito для тестовой отправки. Проверить на том же proxy.
4. Убедиться, что `drive_archive_status` допускает `processing` и `failed` в текущей
   схеме; проверить существующие triggers, UUID staff.id и маршрут authenticated Storage.
5. В тестовом окружении применить миграцию, обновить GAS, функции и env, запустить
   worker; затем обновить клиент. Проверить файл и повтор на реальном Google Drive.
6. Только после этого согласовать production release. Автоматической выкладки нет.

Нельзя запускать старые release-инсталляторы поверх текущей версии или весь `main`
вместо проверенного набора изменений: это может затереть серверные исправления.

## Откат

```sh
systemctl disable --now bos-drive-archive.timer
```
```sh
systemctl stop bos-drive-archive.service
```

Восстановить **собственную резервную копию этой выкладки** функций, web-root и env,
сначала сверив, что после неё никто не публиковал другой релиз. Конкретные команды
копирования будут зависеть от inventory и каталога backup. Сохранить новый GAS:
он совместим со старой подписью и не удаляет файлы. Не откатывать БД целиком,
не удалять очередь/столбец ID проверяющего и не отменять принятые отчёты: миграция
аддитивная. Накопленная очередь останется до восстановления worker. После отката
повторить проверки входа, отчётов и текущего build.
