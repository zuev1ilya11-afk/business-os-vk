# Рекламация № 7395762: подтверждённая причина и исправление

Диагностика на production 31.10.2026, предоставленная пользователем:

- Внутренний ID 1769; статус «Выполнена».
- completed_at и report_reviewed_at: 2026-10-31T14:24:50.693+00:00.
- Рекламация открыта 29 октября; запись order_claims № 4 всё ещё open.
- Сохранённое начисление 3754.79 ₽, допработы 0, повторный выезд бесплатный.
- manual_completion_history пустая; guard_order_completion стирает исходные даты.

Обычная проверка отчёта закрыла заказ и поставила новую дату завершения, но
не закрыла запись рекламации. Читатели финансов отнесли прежнее начисление к
новому периоду. Сумма в заказе не была новым банковским переводом: приложение
не хранит подтверждение фактической выплаты по этой заявке. Пользователь
подтвердил, что исходная работа уже была оплачена.

Исправление в рабочей ветке:

1. Новая закрытая таблица order_financial_snapshots хранит одну исходную
   финансовую запись на заказ. Триггер сохраняет OLD до первого открытия
   рекламации. Повторные открытия не меняют эту запись. Сохраняется ограниченный
   набор дат, сумм, источника, мастера и работ; без контактов и вложений.
2. Операционные статус, отчёты и даты остаются на orders. Финансы, выгрузка и
   зарплатные экраны используют исходную финансовую запись. Бесплатный повторный
   визит не переносит исходное начисление в новый период. Проценты и правила
   допработ не меняются; сохранённая зарплата не пересчитывается по новой цене.
3. Новый мастер на рекламации не получает старое начисление. Первый мастер
   сохраняет свою историю даже после переназначения; API возвращает ему только
   разрешённые поля собственного начисления, без стоимости для компании и
   сведений о новом визите. Операционные списки заявок не расширяются.
4. Триггер закрывает открытую запись order_claims при завершении рекламации,
   включая принятие отчёта. Существующий guard по-прежнему требует отчёт; если
   он отклоняет завершение, вся операция, включая закрытие рекламации, откатывается.
5. Для старой рекламации без истории выводится предупреждение о неполных итогах.
   Период не угадывается. Компактная выгрузка соответствующего мастера блокируется
   с понятным сообщением до восстановления исходного начисления. Полная выгрузка
   сохраняет предупреждение. Исходные суммы в orders не обнуляются.

Таблица доступна только service_role на чтение, с RLS; anon/authenticated
не имеют доступа. Запись выполняет SECURITY DEFINER триггер с пустым search_path.
Старые API с select('*') по orders не получают финансовую историю автоматически.
Роли owner/manager получают проекцию через существующую авторизацию mini-app-api;
мастера — только собственную зарплатную историю, диспетчеры — без истории.

## Восстановление старой даты и выпуск

Исходная дата № 7395762 пока не подтверждена. В тестах сентябрь используется
только как синтетический пример, это не реальная дата этой заявки.

check-claim.py выполняет диагностический SQL в READ ONLY. Режим --backups
показывает метаданные архивов, --recover читает только orders из архивов и
выбирает ID 1769 с совпадением внешнего номера. pg_restore используется как
декодер с --file=-, без соединения с БД и без исполнения архивного SQL.
В выводе только статус, дата, начисление; разрешённые поля кандидатов сохраняются
в приватном файле /tmp/bos-claim-recovery.json с правами 0600 для проверки.
Контакты, вложения и чужие строки в этот файл не попадают.

Резервные копии на сервере найдены. Ожидается результат чтения целевой строки.
Автоматическая миграция не угадывает данные старых рекламаций и не изменяет
orders.master_payout. Точечное восстановление требует подтверждённого исходного
состояния; перед ним необходимо сравнить кандидата с текущей строкой.

Production не обновлён этой веткой. Старый bos-finance.pyz относится к уже
установленной полной выгрузке, его повторный запуск не публикует новую кнопку.
Новый выпуск должен строиться относительно BUILD 76372a6dd138d4168acd, сохранять
существующие RU маршруты и серверный order-payroll.js source-60-40-v1; новая
приватная проекция выгрузки использует модели интерфейса. Нужна проверка пакета
с новой таблицей на изолированной БД и gateway, затем адресная миграция и
восстановление подтверждённой истории. При откате файлов нельзя удалять
финансовые записи, уже сохранённые триггером после установки.
