# Скачивание финансовой детализации

Реализация от 31.10.2026. Работа в ветке `feat/finance-detail-xlsx-20261031`, основание — main `80a97b3`. Production, схема базы, формулы зарплаты, интеграции и статусы не менялись.

## Пользовательский сценарий

Владелец или менеджер открывает «Финансы», выбирает период/фильтры и нажимает «Скачать детализацию». Пока расходы не загружены, кнопка недоступна. Сервер проверяет сессию и актуальные права, возвращает период, число заявок и расходов. Кнопка «Скачать Excel» получает готовый серверный `.xlsx`.

Выполняются только чтения. Повторный клик во время запроса блокируется. Закрытие окна или выход/смена аккаунта отменяют клиентский запрос. Ошибка не выводит серверный текст, токены, SQL или адреса. При пустой выборке файл не создаётся; период только с расходами выгружается. Изменившиеся после предпросмотра данные требуют повторной подготовки. Если суммы сервера уже отличаются от экрана, предлагается обновить «Финансы».

Основные листы: «Сводка», «Заявки», «Работы», «Мастера», «Источники». «Расходы» добавляется при наличии подходящих расходных операций. Во всех листах закреплена строка заголовков, включены фильтры, заданы ширины; суммы — числа с форматом ₽, даты — Excel serial dates, номера/телефоны — текст. Текст не преобразуется в формулы. Ячейки не объединяются.

## Источники действующих расчётов

| Показатель | Текущий источник |
|---|---|
| Выбор периода, финансовая дата заявки | `salary-periods.js`, `finance-data.js: period / records / select` |
| Выручка | `finance-data.js: records`: завершённая заявка, `amount + extra_work_amount` |
| Начисление мастеру | Сохранённый `master_payout + extra_work_amount`. Удержание 6% не применяется; новая формула не вводится |
| Доля компании | `order-payroll.js: companyShare`, только при наличии сохранённого начисления |
| Расходы | `finance_expenses`, `finance-expenses.js: select / summary` |
| Прибыль / «После расходов» | Существующая доля компании минус расходы; не баланс банковского счёта |
| Источники и мастера | `finance-data.js: groups / aggregate` |
| Hands / «Руки» / «Руки (Hands)» | `order-payroll.js: sourceLabel`, единая группа «Руки (Hands)» |
| Лемана Про | Отдельная группа «Лемана Про», без подключения к интеграции Hands |
| Вычеты | Сохранённые `uncompleted_work_amount`, `uncompleted_work_items`; `amount` уже после вычета |

Фильтры периода, источника, мастера, города, работы повторяют текущий экран. При открытой детализации мастера сужается вся выгрузка до него; активный поиск мастера на вкладках «Обзор»/«Мастера» тоже учитывается и показан в предпросмотре. Сортировка и «Показать ещё» не ограничивают состав выгрузки. Фильтра статуса/подразделения в текущем разделе нет — новый фильтр не добавлен и неподдерживаемый фильтр API не игнорирует.

Финансовая дата завершённой заявки: `completed_at`, затем `report_reviewed_at`, затем `scheduled_date`. Для остальных — `scheduled_date`, затем `created_at`. Даты timestamp приводятся к Москве. Для «Всё время» в имени файла стоят крайние известные даты выбранных заявок/расходов, а строки без даты остаются внутри; сводка явно отмечает «Всё время».

## Происхождение колонок

### Заявки

| Колонка | Источник / правило |
|---|---|
| Внутренний ID | `orders.id`, текст без потери точности |
| Номер заявки | `order_number`; иначе номер из `external_id=hands:…`; иначе `id` — тот же fallback, что на экране |
| Источник | `sourceLabel(order)` |
| Дата поступления | `received_date`; если отсутствует, московский день `created_at` |
| Дата согласования | Московский день `master_agreed_at` |
| Плановая дата выполнения | `scheduled_date` |
| Фактическая дата завершения | Московский день `completed_at`; не заменяется датой проверки отчёта |
| Статус | `status` |
| Клиент | `client` |
| Телефон | `phone`, текст |
| Адрес | `address` |
| Город или район | `city`; адрес не разбирается догадками |
| Назначенный мастер | Та же идентификация по `master_staff_id`, сохранённому legacy `master_id` и external ID, что в `finance-data.records`; `business_staff.full_name` / сохранённое `master_name` |
| Основные работы | `record.base` — сохранённый `amount` для завершённых, 0 для незавершённых/отменённых как на экране |
| Дополнительные работы | `record.extras` — `extra_work_amount` для завершённых, иначе 0 |
| Невыполненные работы | `uncompleted_work_amount`, без повторного вычитания из `amount` |
| Скидка | Пусто: отдельного поля в используемом контракте нет |
| Другие корректировки | Пусто: разность `original_amount` и `amount` не объявляется скидкой/корректировкой |
| Итоговая сумма | `record.revenue` |
| Начисление мастеру | `record.pay`, сохранённое начисление + допработы |
| Расходы по заявке | Сумма выбранных `finance_expenses.amount` с совпадающим `order_id` |
| Доход компании | `record.company`, существующая доля компании до расходов |
| Прибыль по заявке | Доля компании минус связанные расходы выбранного периода; при неизвестной доле пусто |
| Способ оплаты | Пусто: поле отсутствует в используемом контракте |
| Статус оплаты | Пусто: не выводится из статуса заявки |
| Комментарий | `orders.comment` |
| Идентификатор отчёта | `report_upload_token`; фотографии/акты не запрашиваются |

Нулевой финансовый вклад активных/отменённых заявок — действующее поведение «Финансов», не утверждение о нулевой согласованной цене. Исходные цены позиций, если сохранены, доступны на листе «Работы».

### Работы

| Колонка | Источник / правило |
|---|---|
| Номер, источник | Идентификатор и нормализация из заявки |
| Дата выполнения | Московский день `completed_at`, иначе пусто |
| Мастер, адрес | Финансовая запись заявки / `address` |
| Название | `work_items[].name` плюс ручной текст `work`, оставшийся после удаления сформированного суффикса этих позиций; для старых заявок — строки `work`; для допработ — `extra_work_description`; для вычетов — `uncompleted_work_items[].name` / сохранённое описание |
| Тип | Основная / дополнительная / невыполненная, по соответствующему полю-источнику |
| Количество | `work_items[].quantity`, `uncompleted_work_items[].quantity`; для старых строк — только явно записанное после ×/x число |
| Единица | Сохранённая `unit`; для старой строки — записанная единица или точное совпадение названия с каталогом |
| Цена за единицу | Только сохранённая `unit_price`, без сегодняшнего прайса |
| Стоимость позиции | Только сохранённый `amount` позиции; для неструктурированных допработ/вычетов — их сохранённая общая сумма |
| Процент / правило мастера | Для основных/невыполненных позиций пусто: историческое правило на позицию не сохранено. Для допработ — действующее правило полного начисления сохранённой суммы мастеру |
| Начисление по позиции | Основные/невыполненные — пусто, общая зарплата не распределяется искусственно. Допработы — сохранённая сумма только завершённой заявки |
| Комментарий | Сохранённое `uncompleted_work_description` для строк вычетов; иначе пусто |

Основные позиции показывают исходный состав; вычеты показаны отдельным типом. Сумма всех типов листа «Работы» не является выручкой. Для неструктурированных допработ количество и цена единицы пустые: число 1 не подставляется.

### Мастера

| Колонка | Источник / правило |
|---|---|
| Мастер | Группировка по стабильному ID `finance-data.groups`; текущие имена из staff, сохранённые имена для истории |
| Назначенные / завершённые заявки | `group.total` / `group.completed` выбранных заявок; история переназначений не выдумывается |
| Выполненные работы / допработы | `group.revenue` / `group.extras` |
| Невыполненные работы | Сумма сохранённых вычетов завершённых заявок; пусто при отсутствии значения хотя бы в одной |
| Зарплата | `group.pay` |
| Расходы | Явный `employee_id` расхода, иначе мастер связанной заявки; каждая операция учитывается один раз |
| Доход компании | `group.company`, до расходов |
| Средний чек | `group.average` |
| Возвраты или исправления | Число уникальных `order_claims.id` по выбранным заявкам, открытых в периоде (`opened_at`, МСК), у мастера `master_staff_id` претензии. Это сохранённые претензии, не количество возвратов денег |

### Источники

| Колонка | Источник / правило |
|---|---|
| Источник | Нормализация `sourceLabel`, без дубликатов Hands/Руки |
| Заявки / завершённые | `group.total` / `group.completed` |
| Общая стоимость | `group.revenue` |
| Зарплата | `group.pay` |
| Расходы | Суммы операций по источнику связанной заявки |
| Доход компании | `group.company` |
| Прибыль | `group.company - group.expenses`; пусто при неизвестной доле |
| Средний чек | `group.average` |

Общие расходы остаются в группе «Без привязки к источнику» / «Без мастера», а не размазываются по заявкам. Расходы в выбранном периоде по заявкам другого периода остаются в соответствующей группе, даже если у неё нет выполненных заявок. Поэтому прибыль источников сходится со сводкой. Сумма прибыли по заявкам может отличаться на общие расходы и расходы по заявкам вне периода — это отражено в сводке.

| Категория | `finance-expenses.label(category)` |
| Описание | Сохранённый `comment` (отдельного поля description нет) |

### Сводка

Период/фильтры берутся из запроса, время формирования — серверное, МСК. Количество и денежные итоги — `finance-data.aggregate`, расходы/прибыль — `finance-expenses.summary`. Стоимость основных работ суммирует `record.base` завершённых заявок. Вычеты — сохранённые `uncompleted_work_amount`. Скидки/другие корректировки пустые. Блоки источников/мастеров повторяют соответствующие группы листов. Отсутствие сохранённой суммы не подменяется нулём или расчётом по сегодняшнему проценту.

## Найденные существующие различия, оставленные без изменения

1. Главная панель владельца показывает основные работы без допработ; «Финансы» включает допработы. Excel следует «Финансам».
2. Фильтр по работам в «Финансах» использует совпадение строки `work` с каталогом; лист «Работы» раскрывает сохранённые структурированные `work_items`. Финансовая фильтрация не переписана.
3. Описание старой методики внизу экрана содержит устаревшую оговорку о Hands. Экспорт использует фактический текущий `companyShare`, не текст подсказки.

## Доступ, объём и развёртывание

Используется существующий endpoint mini-app-api и его подписанная X-BOS-Session. Активная роль берётся с сервера: owner/manager. Мастер, диспетчер, неактивный сотрудник, отсутствующая/поддельная/истёкшая сессия не получают данные. Подставленные role/permissions/списки заявок в теле ничего не разрешают. При снятии прав между двумя запросами скачивание запрещается заново.

В API два действия: `previewFinanceExport` и `downloadFinanceExport`. Файл не сохраняется в публичном storage, response `private, no-store`. Источники запросов перечислены явно; фото, акты, пароли и сырой payload интеграций исключены. Пагинация — 1000 записей. При сканировании заявок удерживаются только строки выборки и заявки, связанные с расходами. Ограничения одного файла: 50 000 удерживаемых записей на набор данных, 250 000 строк работ, 128 MiB потока XLSX. Это защитные пределы, не скрытое усечение. Для превышения объёма нужно уменьшить период; ошибки потока показываются как ошибка формирования.

OOXML/ZIP формируется на сервере последовательно с backpressure и отменой, без больших XML-строк и новых npm-зависимостей. Браузер получает готовый Blob; действующий транспорт может буферизовать ответ. Для этих двух read-only действий бюджет увеличен до 120 секунд: до 25 секунд на gateway, остаток — прямому endpoint. При сетевом сбое/502/503/504 допускается безопасная повторная попытка другим маршрутом; ответы 401/403/409 не повторяются. Правила повтора записывающих действий приложения не изменены. Ограничение конкретного reverse proxy/Edge runtime требует проверки на staging.

**После отдельной команды на публикацию** потребуется обновить и frontend, и mini-app-api с новым `_shared/finance-export.ts`, `_shared/finance-xlsx.js` и импортируемыми корневыми JS-модулями. Одна публикация статических файлов недостаточна. Миграции БД не нужны. До разрешения на merge/deploy рабочая версия не меняется.

- `npm run build` и `npm run build:check` — успешно; BUILD_ID `90a77c9afe9c5c494a4e`.
- Полный `npm test`: **819 серверных тестов и 876 браузерных тестов прошли**, ошибок нет. Пять существующих opt-in проверок пропущены: один внешний health check архивного GAS и четыре сценария создания иллюстраций помощи (`BOS_TEST_ARCHIVE_GAS` / `BOS_CAPTURE_HELP` не включались).

- `deno check --node-modules-dir=manual --no-lock supabase/functions/mini-app-api/index.ts` — успешно на Deno 2.9.6. `deno lint` для четырёх новых production-модулей — успешно; `node --check` изменённых JS и `git diff --check` — успешно. В репозитории нет общего npm-скрипта lint; линтер старых несвязанных модулей не заявляется как пройденный.
- Пример прошёл открытие/пересохранение LibreOffice в `.xlsx`; независимая проверка полученного ZIP/XML подтвердила шесть листов, дату 01.10.2026 как Excel date, числовое начисление 600 и прибыль 350 в первой заявке.
- Независимое ревью завершено. Исправлены и покрыты регрессиями сохранение ручного текста работ, legacy `master_id`, исторические имена неактивных мастеров в расходах/исправлениях и fallback после 504 для длительной выгрузки.

Проверки выполнены на синтетических данных через настоящий обработчик API и генератор файла с подменой границы базы данных. **Доступа к реальным заявкам не было: сверка карточка → «Финансы» → Excel на production-данных не выполнена.** Ручная совместимость Microsoft Excel/Google Sheets и лимиты размещённого Edge/gateway требуют проверки на staging. Merge и публикация не выполнялись.
