# Контроль договорённостей: пилот

PR реализует этап 1 в существующем business-os-vk. Российский production не менялся. Миграция, серверный API и интерфейс подготовлены в отдельной ветке; оба флага по умолчанию `false`.

## Что переиспользовано

- `master-call-workflow-v26.js`: существующая форма результата звонка и явное подтверждение разговора.
- `master-order-actions-v179.js`: действие «Договорились» и существующие поля расписания (`scheduled_date`, `scheduled_time`, `time_slot`, `master_agreed_at`).
- `master-workflow-api`: существующая подписанная сессия и проверка сотрудника/доступа; сведения о зарплате по-прежнему скрыты от мастера.
- `master_contact_history`: журнал контактов; старые записи сохранены, события пилота не обрезаются.
- `bos_control_private.tasks`, `bos_control_action`, `order-control.js`, `order-control-tasks.js`: существующие поручения и раздел контроля.
- `bos_push_subscriptions`, `bos_push_deliveries`, claim/delivery/finish: существующий дополнительный push-канал. Статус «принят сервисом» не означает показ на телефоне.
- Фактическая инфраструктура по `deploy/pr289`: существующий PostgreSQL и Edge Runtime на российском сервере. Новая БД, облачный проект и новые интеграции не нужны. Legacy URL в исходниках не переопределялись; используется действующая упаковка RU-релиза.

## Поведение

Результат, серверный журнал, ревизия заявки и поручение сохраняются в одной транзакции `bos_contact_action`. `expected_revision` защищает от устаревшего окна. Повтор того же `attempt_id` подтверждается без новой записи; изменение его содержимого отклоняется. Даже повтор старого успешного запроса после нового результата не восстанавливает старое поручение.

| Итог | Обязательно | Контроль |
|---|---|---|
| Не дозвонился | Следующий контакт | Поручение мастеру; успешный разговор не отмечается |
| Клиент думает / ждёт доставку / перезвонить позже | Следующий контакт | Поручение мастеру; дата визита не подставляется |
| Договорились | Дата и время визита | Сохраняется визит, актуальное поручение контакта закрывается |
| Требуется помощь / клиент отказался | Причина | Поручение ответственному руководителю; мастер и жизненный статус не меняются |
| Другое (совместимость) | Комментарий и следующий контакт | Поручение мастеру |

Нажатие телефона добавляет попытку `pending`, но не успешный контакт. Договорённость сохраняет длительность из достоверного существующего интервала; неизвестная длительность не выдумывается, выход за сутки отклоняется. После начала работ/отчёта обычное изменение визита запрещено существующей границей процесса.

Черновик формы хранится в `sessionStorage` отдельно для сотрудника и заявки; переживает потерю ответа и перезагрузку той же вкладки. Кнопка обновления при конфликте загружает свежую заявку и оставляет поля для проверки. Черновик не обещает пережить закрытие вкладки/очистку браузера. Время формы и серверных правил — `Europe/Moscow`, независимо от часового пояса телефона.

## Подключение пилота после отдельного согласования

1. Сохранить резервную копию существующей БД. Применить миграцию `20261015163150_contact_control_pilot.sql` после текущих миграций контактов/control/push. Она добавляет только поля/функции/настройки, не создаёт поручений по историческим данным и не включает таймер или push.
2. Развернуть обновлённый `master-workflow-api` существующим RU-процессом и frontend с согласованным build ID. Изменения в исходном API не попадут в старый `deploy/pr289/bos289.pyz` сами: для будущего релиза нужен новый пакет из этой ветки. Публикация PR289-пакета эту функцию не установит.
3. Выполнить read-only `scripts/contact-control-preflight.sql` в **той же** БД. Записать 3–5 действующих UUID мастеров, действующего owner/manager, рабочие дни и часы компании. В PR нет реальных сотрудников, рабочего окна и секретов.
4. В `bos_control_private.contact_config` заполнить `pilot_staff_ids`, `manager_id`, `company_start`, `company_end`, `company_days`. Дни ISO: 1=пн, 7=вс. Только затем установить `enabled=true`. Guard отклоняет включение без обязательных настроек. Проверить, что все UUID действительно имеют роль master и активны; это также показывает preflight.
5. Проверить формы на специально заведённых тестовых заявках и включить `reminders_enabled=true` отдельным изменением после согласования. Push runtime и его endpoint не включать/менять автоматически.
6. Подключить **один** серверный таймер из вариантов ниже. Проверить журнал запусков и отдельное тестовое поручение. Не создавать тестовые события в реальных рабочих заявках.

| Параметр | Подготовленное значение | Правило |
|---|---|---|
| `enabled` | false | Требования формы/новое подключение к пилоту |
| `reminders_enabled` | false | Автоматические стадии напоминания/эскалации |
| `pilot_staff_ids` | пусто | Только явно выбранные мастера; начать с 3–5 |
| `manager_id` | NULL | Один ответственный руководитель пилота |
| `first_contact_minutes` | 60 | Рабочие минуты после нового назначения |
| `escalation_minutes` | 120 | Предложение для согласования; рабочие минуты после срока |
| `reminder_limit` | 1 | 0 отключает push, 1 допускает одну попытку на адресата/версию/устройство; бесконечных повторов нет |
| Рабочее окно/дни | NULL | Обязательное явное fallback-окно компании |
| Часовой пояс | Europe/Moscow | Существующее бизнес-время |

`staff_schedule` конкретного дня имеет приоритет: явный выходной не заменяется рабочим окном компании. Если строки нет, используется окно компании. Записанный выезд/начало работ с достоверным интервалом текущего дня отодвигает начало отсчёта; одно плановое время без выезда этого не делает. Незавершённые поручения не исчезают при недоставке push.

Историческая заявка подключается только при новом назначении пилотному мастеру после включения либо явном сохранении нового результата для пилотного мастера. Сканирования и массового backfill нет. При переназначении уже открытое обязательство передаётся новому мастеру **даже вне allowlist**, со старым сроком и накопленной эскалацией; allowlist ограничивает новые подключения. Это не даёт новому мастеру права на остальные заявки.

## Серверный таймер

`bos_control_private.tick()` продвигает автоматические стадии и существующие ручные поручения. Push не нужен для появления просрочки/эскалации в приложении. За один вызов обрабатываются до 200 доступных заявок; обработанные стадии не блокируют следующие. Параллельные вызовы используют блокировку order → task с `SKIP LOCKED`.

- Если действующий cron уже вызывает `bos_control_private.tick()`, использовать его, не добавлять второй.
- Если в существующей БД настроен `pg_cron`, после согласования выполнить `supabase/contact-control-scheduler.sql`. Именованное задание запускается раз в минуту; повтор скрипта обновляет то же имя. Расширение не устанавливается этим скриптом.
- Если `pg_cron` отсутствует, в `deploy/contact-control/` подготовлен host systemd timer. Администратор должен выбрать существующего OS/DB-пользователя, заполнить `/etc/business-os/contact-control.env` из примера, проверить путь `psql` и подключение к существующей БД. Установить unit-файлы в `/etc/systemd/system`, выполнить daemon-reload и enable/start timer только после разрешения. Пароли — в защищённом существующем `.pgpass`, не в Git. Стандартный журнал — `journalctl -u business-os-contact-control.service`; ненулевой код psql виден как ошибка unit.

Сам по себе push maintenance **не вызывает** control tick в текущем коде. Отсутствие таймера нельзя считать готовым серверным пилотом. Фактические cron/systemd, DB credentials и worker на production в этой задаче не проверялись и не менялись.

## Отключение и возврат

- Остановить только автоматизацию: `UPDATE bos_control_private.contact_config SET reminders_enabled=false WHERE singleton;`. Задачи/результаты видны, их сроки сохраняются.
- Выключить новые требования пилота: `UPDATE bos_control_private.contact_config SET enabled=false, reminders_enabled=false WHERE singleton;`. Данные не удаляются. Обычные операции, отчёты, файлы и завершение продолжают работать. Сохранение legacy-итога при выключенном флаге закрывает старое автоматическое обязательство, чтобы оно не ожило после включения.
- Sender повторно проверяет оба флага, версию, назначение и закрытие перед отправкой уже взятой задачи. Не выполняется компенсация push, уже принятого внешним сервисом до выключения.
- Если потребуется откат frontend/API, оставить additive-схему и выключенные флаги. Миграцию с данными не удалять. Для остановки нового timer отключить только `bos-contact-control` cron/job или одноимённый systemd timer, не общий push/recovery.

## Проверки и ограничения

Подробные фактические результаты фиксируются в [verification.md](verification.md). SQL-контракты проверяют атомарность, все итоги, ревизии/retry, доступ, графики, выезд, переход суток, очередь >200, остановку при закрытии, переназначение, sender guard, повтор миграции и совместимость ручных поручений. В тестах HTTP/Vault контролируются заглушками, рабочие заявки/клиенты не используются.

Локальные изображения сценариев показывают существующий интерфейс на синтетических fixture-данных. Это не проверка production, push на телефоне или работающего production-планировщика. Для настоящего серверного Preview необходим отдельный разрешённый staging endpoint существующей инфраструктуры; такой endpoint/доступ в сессии не предоставлен.
