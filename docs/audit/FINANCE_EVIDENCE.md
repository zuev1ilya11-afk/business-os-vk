## Подтверждённый дефект и исправление

**FIN-01 · P2 · потеря результата частичного импорта при исключении RPC.**

Триггер: из нескольких выбранных строк одна уже сохранена; следующий вызов
`bos_import_lemana_order` выбрасывает транспортное исключение. До исправления
внешний `catch` возвращал HTTP 400 и текст исключения, теряя сведения об уже
созданных строках. Ответ мог содержать внутренний адрес из сетевой ошибки.

В [`lemana-api.ts`](../../supabase/functions/_shared/lemana-api.ts) исключение
обрабатывается для конкретной строки. Подтверждённые результаты сохраняются;
строка с потерянным ответом получает сообщение «Результат сохранения строки не
подтверждён. Повторите предпросмотр». Последующие строки обрабатываются; повтор
защищён существующей create-only RPC. Не утверждается, что потерянный ответ
означает отсутствие записи в базе.

Регрессия в [`lemana-api.test.cjs`](../../tests/lemana-api.test.cjs): три
синтетические строки, потеря ответа **после фиксации второй**, затем повтор.
До изменения: тест падал (400 вместо результата по строкам). После: два
подтверждённых создания, одна неопределённая строка; при повторе три пропуска,
ровно три записи. Внутренний текст исключения не возвращается.

Миграции и пересчёт данных для этой правки не нужны. Включение исправления в
production требует предварительного сопоставления фактического RU backend
с исходниками; замена всей веткой не подготовлена и не разрешена.

## Ограничения и дальнейшая работа

### Повтор ручного создания

Отдельно проверен сценарий **успешной записи с потерянным ответом**: новый
[`order-create-lost-response.spec.js`](../../tests/order-create-lost-response.spec.js)
выполняет настоящий frontend и изолированный `mini-app-api`, затем выбрасывает
ошибку на клиенте после сохранения. Повтор в той же открытой форме получает
исходную заявку; в базе и локальном списке остаётся одна строка. **1/1** в
Chromium headless-shell, внешний трафик запрещён proxy. Изменение рабочего кода
для этого сценария не потребовалось.

Механизм: `master-order-flags-patch.js` / `schedule-identity-v46.js` хранят
`request_id` в `#orderForm.dataset`; `mini-app-api` ищет
`external_source=mini_app`, `external_id=app_<actor>_<request_id>` и при unique
conflict повторно читает исходную строку. Существующие `order-intake.spec.js`
проверяют двойной клик и сохранение черновика при отказе до записи;
`server-audit.test.cjs` — конкурентный повтор с одинаковым ключом в mock-БД.

**Граница защиты:** ключ находится только в DOM открытой формы. После
перезагрузки страницы/закрытия формы новый ручной ввод получает новый ключ.
Если результат предыдущего создания неизвестен, сначала требуется проверить
список существующих заявок. Автоматическая защита после потери формы не
подтверждена; сохранение незавершённого request ID/восстановление результата —
отдельная задача модернизации. Дедупликация одновременных запросов также
требует действующего уникального индекса `(external_source, external_id)`:
его наличие описано в `docs/AVITO-INTEGRATION.md`, но фактическая production
схема в этом аудите не прочитана.

Состояние production-таблиц, применение миграций, фактический runtime и
заявка № 7395762 в этом аудите не прочитаны: нет проверенного доступа к БД.
Тесты на синтетическом аналоге не подтверждают исправность конкретной рабочей
заявки. Настоящие выплаты и остаток денег требуют первичных платёжных записей;
текущая выгрузка мастеру прямо обозначает **начисления**, а не факт выплаты.
Отдельный журнал выплат и сверка остатков — задача модернизации, не повод
пересчитать существующие деньги по предположению.

Фоновый Hands, реальный импорт из кабинета и уведомления не запускались.
Пакетный импорт требует сохранения текущего create-only ограничения при любом
последующем рефакторинге. Для нового источника прайса полезно закрепить этот
read-only сверяющий шаг в процедуре обновления и проверять сохранение старых
цен на закрытых заявках.
