## Конкретный результат разработки

Подготовить отдельный пакет `deploy/recovery/` с командами подготовки копии, проверки копии и восстановления **только в отдельную среду**. Выдать один обезличенный JSON-отчёт и короткое резюме. Команды оператора — не длиннее 60 символов; большие действия находятся в проверенном файле.

1. Автоматический preflight: подтвердить release/build, однозначный маршрут БД и реальные Storage mounts; проверить место, права, целевой путь и отсутствие совпадения с рабочими томами. Не запрашивать у владельца повторную ручную сверку. При изменившейся базе остановиться с одним конкретным кодом причины.
2. Сохранить БД штатным средством PostgreSQL, необходимые роли/права, Storage, артефакты web/Edge, версии образов и требуемую конфигурацию восстановления. Не архивировать сырые файлы работающего PGDATA как готовый backup. Секреты и данные — только в закрытом комплекте с ограниченными правами; не в Git, терминальном выводе или чат-отчёте.
3. Явно определить согласованность DB+Storage при продолжающихся записях. Два независимо снятых архива без этой гарантии не получают статус готовой копии. Если нужна остановка записи, подготовить конкретную процедуру и окно; не выполнять её в рамках read-only аудита.
4. Сделать контрольные суммы и manifest состава; получить независимую копию за пределами исходного сервера, затем вернуть её для restore-теста. Каталог на том же диске не считать независимой копией. Целевое хранилище пока не выбрано; не выдумывать адреса или доступы.
5. Восстанавливать в новые ресурсы с отдельными именами, сетью, томами, ключами и origin. Блокировать исходящие обращения до запуска восстановленных служб, включая фоновые задания в БД; не допускать реальных push, Avito, Hands, Google и рабочих webhook. Если изоляцию нельзя доказать, восстановленный сервис не запускать.
6. Проверить права, связь записей Storage с файлами, контрольные объекты и возможность запуска нужных частей приложения на восстановленном runtime. Отсутствующие исходники/issuer обозначить как блокер полной копии; не подменять её synthetic fixture-стендом.
7. Измерить длительность восстановления и фактическую точку данных. Цели RPO ≤1 часа и RTO ≤4 часов из плана остаются ориентирами до измерения. Если целый стек поднят, выполнить на копии сценарий «создание → контакт → отчёт → проверка → финансы», сохранение после reload и доступ к фото/акту. Зафиксировать отдельно результат restore и сквозного сценария.

## Проверка пакета до запуска владельцем

Тестировать существенные отказы: смена release/build, неоднозначный маршрут, неверная цель, заполненный диск, ненулевой exit dump, повреждённый/неполный архив, прерванный процесс, запрещённые исходящие обращения, попытка восстановления в live. Секреты не попадают в отчёт даже при ошибке. Незавершённый комплект не помечается успешным; cleanup затрагивает только созданные пакетом временные ресурсы.

Проверить реальный цикл dump→restore на изолированной тестовой PostgreSQL и тестовом Storage; mocks не заменяют эту проверку. Только затем давать короткий запуск для подтверждённой серверной базы. До запуска на сервере нельзя заявлять, что рабочие данные сохранены или восстановлены.

### V2: остановка на проверке базы и чтение сохранённого журнала

Следующий скриншот оператора `image(20261115-173908).png` показывает переход к `APP_STAGE=DATABASE`, затем `APP_DOCKER_COMMAND_FAILED`, failed_service `db`, category `MISSING_RUNTIME_FILE`, evidence_bytes 1482. Неудачный clone `bos-app-04be1a710f3f-data` сохранён; baseline по отчёту прежний `bos-drill-f18143a443fb-data`. Приложение не запущено, `disaster_recovery_ready=false`.

Код сужает место сбоя до SQL-проверки после запуска БД: clone и single-user bootstrap выполняются до этапа DATABASE; неперехваченный `APP_DOCKER_COMMAND_FAILED` в этом этапе возникает в бинарном SQL-вызове проверки. При этом `_private_logs` может заменить stderr неудачной команды всем журналом DB-контейнера. Поэтому прежняя общая категория не доказывает отсутствующий runtime-файл: её могло породить другое сообщение журнала. Точная причина без сохранённого журнала ещё неизвестна.

Добавлен отдельный `check-db.cmd`, который читает три фиксированных файла журналов только из существующего неудачного clone. Manifest должен совпасть с успешным restore-report; private-config проверяется по хешу, образ — по сохранённым метаданным. Helper использует уже локальный точный DB image, явный shell вместо исходного entrypoint, network none, read-only rootfs и единственный volume mount read-only. Проверяются метки, отсутствие чужих ссылок на том и параметры изоляции. БД не запускается, baseline не монтируется, новые тома не создаются, backup и данные не изменяются. После чтения удаляется только собственный helper.

В `BOS-DB-Diagnostic-*.json` выходят фиксированные категории, известные PostgreSQL идентификаторы, классы путей и ограниченный словарь сообщения; произвольные значения, SQL, DETAIL/HINT/CONTEXT и исходные строки не публикуются. ERROR/FATAL/PANIC отделены от startup LOG/WARNING/NOTICE, чтобы второстепенное сообщение не подменяло причину ошибки. Это сбор доказательств, а не исправление ещё неизвестного дефекта и не успешный запуск private backup. Следующий runtime fix зависит от результата этой проверки.

Прочитан `BOS-DB-Diagnostic-20261115T180017Z-c5a5ebc3.json`: DB log 1482 байта, один FATAL `LOCALE_OR_COLLATION_FAILURE` с сообщением `database locale is incompatible with … system`. Postmaster успешно слушает сокет и сообщает readiness; ошибка возникает при подключении к восстановленной прикладной БД. Bootstrap log ошибок не содержит. Диагностика подтвердила read-only mount существующего failed clone, отсутствие запуска PostgreSQL, создания новых томов и подключения baseline.

Причина в app runtime: `clean_env` очищал image ENV `LOCALE_ARCHIVE`, а оба вызова `postgres` через `env -i` оставляли только PATH. В Nix-образе Supabase PostgreSQL 17 архив локалей подключается через `/nix/var/nix/profiles/default/lib/locale/locale-archive`. Успешный restore сохранял эту переменную образа; старый app CI создавал БД с C locale, поэтому не замечал потери архива. PostgreSQL выполняет setlocale по catalog LC_COLLATE/LC_CTYPE; этот FATAL не является предупреждением о версии collation.

V3 передаёт только разрешённый путь LOCALE_ARCHIVE из проверенных immutable image metadata в холодный bootstrap и обычный postmaster. Произвольные container ENV, LOCPATH, LD_PRELOAD, PG routing и секреты по-прежнему не передаются. При неизвестном пути или нечитаемом архиве запуск останавливается. Locale/collation в каталогах БД, индексы и dump не переписываются. Stderr неудачной команды теперь сохраняется отдельно и имеет приоритет перед startup LOG в публичной классификации.

Регрессионная проверка использует настоящую libc locale `en_US.UTF-8`: прежнее окружение должно воспроизвести FATAL, исправленное — пройти полный capture → restore → clone → шесть служб. Сравниваются datlocprovider/datcollate/datctype/datlocale/datcollversion между исходной, восстановленной и рабочей БД. Проверки на private backup и пользовательские действия остаются следующим операторским шагом.

Первичные основания: [Supabase Dockerfile-17](https://github.com/supabase/postgres/blob/develop/Dockerfile-17), [Nix glibc archive lookup](https://github.com/NixOS/nixpkgs/blob/master/pkgs/development/libraries/glibc/nix-locale-archive.patch), [PostgreSQL CheckMyDatabase](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/utils/init/postinit.c).

### V4: Auth connection search_path и диагностика всех служб

Прочитан `BOS-App-20261115T182136Z-090a5afe.json`. V3 на частной копии прошла DATABASE: CLONE_VALIDATED, 311 orders, 19 staff, 1060 Storage objects. Следующая остановка SERVICES/auth: APP_CONTAINER_NOT_RUNNING, PERMISSION_DENIED, 599 байт evidence; сохранён `bos-app-3a4a2468d519-data`. Сам журнал Auth пока не передан, поэтому конкретная схема/файл из операторского отчёта неизвестны.

Обнаружен самостоятельный дефект настройки Auth: bootstrap удаляет pg_db_role_setting, включая обычный role search_path=auth, а migration ledger GoTrue использует неквалифицированный schema_migrations. Старый CI ошибочно выдавал Auth CREATE в public, скрывая потерю пути. V4 добавляет ровно один сгенерированный search_path с процитированным проверенным namespace в свежую локальную URI Auth. Параметр действует только на соединения Auth; права, shared-role defaults и произвольные архивные GUC не восстанавливаются. Поддерживаемые namespace aliases должны совпадать. Storage по upstream сам задаёт свой search_path; его runtime не меняется.

Регрессия воспроизводит обычную установку Auth с role search_path=auth и без CREATE в public: отсутствие URI search_path должно приводить к SERVICES/auth, permission denied for schema public, SQLSTATE 42501. Исправленная копия должна пройти Auth health, сохранить schema owner, migration versions и ACL. Для Storage также исключён CREATE в public, чтобы проверить следующий сервис при ограниченных правах.

Новый полный BOS-App JSON содержит обезличенные сведения о журналах всех уже запущенных служб. Поддержаны GoTrue JSON logs и SQLSTATE; исходный SQL, неизвестные значения, пароли и клиентские данные не экспортируются. Console вывод сокращён до этапа, сервиса, категории и пути к полному отчёту. Дополнительный check-services.cmd читает fixed service logs из существующего failed clone только read-only без запуска PostgreSQL и создания новой копии. Private startup всё ещё требует следующего операторского запуска; CI не заменяет вход сотрудника и бизнес-сценарии.
