# Безопасные изменения Business OS

1. Получить свежий `main`: `git fetch origin`, создать отдельную `feature/...` или `fix/...` ветку от `origin/main`. Не работать напрямую в `main`.
2. Одна задача — одна ветка. Не использовать одну ветку одновременно для разных задач или агентов.
3. До правок проверить открытые PR и пересечение файлов. Не переносить изменения параллельного PR без необходимости.
4. Изменять исходные JS/CSS/HTML. Не менять вручную BUILD_ID, cache-bust/query-параметры или версии в `index.html`, `pwa-register.js`, `sw.js` и `build-version.js`.
5. После frontend-правок выполнить `npm run build`. Он автоматически обновляет BUILD_ID, HTML, manifest с SHA-256 и Service Worker. Новые корневые JS/CSS/assets автоматически входят в manifest; подключать lazy-модули через `BOS_ASSET_URL`.
6. Выполнить необходимые targeted tests, затем обязательные проверки: `npm run build:check`, `npm run test:server`, `npm run test:ui -- --workers=2`. Закоммитить исходники вместе с generated-файлами. CI отклоняет устаревшую сборку с указанием выполнить build.
7. Открыть PR. Перед merge снова проверить актуальность относительно `main`. При обновлении от `main` сохранить обе нужные правки, заново выполнить build и проверки.
8. Дождаться полностью зелёного GitHub CI на последнем HEAD. Не сливать красный CI и не обходить проверки.
9. Если два PR меняют один файл, второй PR после merge первого должен отдельно обновиться от нового `main` и разрешить конфликт заново.
10. После merge дождаться успешного GitHub Pages deployment. Проверить production: BUILD_ID, вход, роли, JS/CSS без 404, регистрацию SW и отсутствие циклических reload/update notices. URL приложения не менять.

Обновление PWA предлагает «Обновить» / «Позже». Перед подтверждением сохранить работу; другие вкладки не должны перезагружаться автоматически. Повреждённый deployment не должен активировать новый SW — предыдущая проверенная сборка остаётся fallback.
