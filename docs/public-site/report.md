# Публичный сайт и клиентский кабинет — отчёт 06.11.2026

Реализован изолированный сайт с общим клиентским API и общей заявкой Business OS. Production, DNS, production-миграции, реальные SMS, платежи, секреты и юридические документы не изменялись. Изолированный Docker-стенд проверен в CI. Готовность к staging на российском сервере зависит от измерений и настроек, перечисленных ниже.

## 1. Найденное и выбранная база

PR #303 уже содержит OTP, сессии, согласия, клиентский PWA, общие orders, версии смет, сообщения, защищённые фотографии, привязку клиентов, обращения и назначение мастеров. Переиспользована эта реализация, отдельная клиентская система не создавалась.

Работа выполнена в отдельном worktree и ветке `feat/public-site-client-integration-20261106`, основание — `5fe15267` ветки `feat/client-portal-20261105`. Проверенный main — `80a97b37`, клиентская ветка содержит 20 дополнительных коммитов, включая финансовые исправления. Исходная клиентская ветка не изменялась. Подробная матрица аудита — [architecture.md](architecture.md).

## 2. Архитектура и выполненная функциональность

Самостоятельно собираемый Next.js / React / TypeScript в `apps/public-site`. Публичные страницы серверно рендерятся. Собственные тексты, CSS, SVG и структура; материалы DeliApp не переносились.

Сайт → контролируемый API PR #303 → общая PostgreSQL и orders → существующий Business OS. В изолированном стенде PostgreSQL исполняется через PGlite. Сотрудники, клиент и сайт используют одну заявку с источником `website`; UTM и признак уточнения связаны с её ID. Файлы и чат проверяют владельца заявки. Повторные отправки используют idempotency.

Безопасная первая конфигурация: сайт и существующий PWA `/client/` на одном origin через nginx, сотрудники — на отдельном техническом origin. Отдельный поддомен PWA отложен до проверки SSO: переносить cookie на все поддомены или передавать токен в URL не стали.

Каталог — публичные метаданные к общему `service-catalog.js`, без второго числового прайса. Режимы fixed/range/from/after_inspection, подтверждение fingerprint цены владельцем/руководителем, сброс числовой цены после изменения источника. На стенде 10 связанных услуг в 6 категориях, все цены первоначально «После уточнения». Длина учитывается как количество для погонных единиц; остальные неутверждённые условия требуют согласования. Поиск: русская полнотекстовая выдача плюс управляемые синонимы.

12 логических этапов оформления объединены в 6 экранов: работы; параметры/описание/фото; адрес/время; контакты; стоимость/согласия; OTP/создание/переход в кабинет. Есть сценарий «Не знаю, что выбрать», сохранение введённого в памяти при потере сети, повтор загрузки фотографий без повторной заявки.

Переиспользованы назначение мастера, согласование даты, чат, сметы и гарантийные обращения. Добавлены отдельно согласованный публичный телефон мастера, статус по фактическим отметкам выезда/начала, защищённый просмотр акта, отзыв после завершения с согласием и модерацией. Гарантия не переоткрывает оплаченный заказ и не меняет начисления.

B2B создаёт отдельный лид `website_business`, а не обычную заявку. Есть очередь сотрудников, статусы, UTM, журнал событий и счётчик новых обращений. Реальные push/SMS менеджерам не подключались.

при нелокальном origin, а установщик задавал HTTPS hostname без opt-in.

Исправление добавляет отдельный точный `WEBSITE_STAGING_HTTPS_ORIGIN` только
для изолированного website staging в явно обозначенном контейнере.
Production/test-delivery guards, проверка входящего Origin и отдельная БД
сохранены. Публичный вход всего стенда закрывается Caddy Basic Auth.
Нужна пересборка и запуск нового staging-образа перед повторной публикацией.

Локально прошли 45 клиентских, 15 website и 11 publisher tests плюс build:check.
Новый тест перезапускает сохранённую PGlite с HTTPS origin, проверяет
отклонение чужого origin и Secure cookie тестового входа. В CI добавлена
аналогичная проверка **собранного Docker-контейнера**, включая страницы,
форму расчёта и login, чтобы этот сбой больше не скрывался за локальным smoke.
Фактический повторный выпуск/сертификат/браузерный доступ требуют проверки
по следующему результату с сервера; здесь они не объявляются успешными.

07.11: полный CI исправления HTTPS origin (`8520e45`, run `42287806564`)
завершился успешно, включая настоящий Docker restart с HTTPS origin.
Пользователь подтвердил Healthy нового контейнера на RU. Следующая попытка
остановилась на сравнении активной конфигурации Caddy, затем `ROLLBACK_OK`.
В установщике устранено сравнение JSON временного кандидата с JSON конечного
Caddyfile: `file_server` включает имя этого файла в неявный список `hide`.
Установщик компилирует конечный путь, загружает этот точный JSON и сохраняет
строгую проверку совпадения. Откат загружает точный прежний активный JSON.
В Caddy smoke добавлена настоящая раздача статического файла и воспроизведение
различия имён; unit-тест отдельно проверяет, что реальное несовпадение по-прежнему
вызывает откат. Runtime сайта в этом исправлении не меняется.

07.11: после успешного применения конфигурации проверка HTTPS завершилась
таймаутом и `ROLLBACK_OK`. Присланный журнал Caddy установил причину: Let's
Encrypt HTTP 429, 50 сертификатов для общего зарегистрированного домена `qd.je`
за 168 часов, retry-after `2026-11-07 12:07:44 UTC`. Это общий лимит зоны,
а не 50 выпусков для сайта пользователя.

Для нового hostname добавлен отдельный issuer ACME ZeroSSL. В исходном коде

берётся из однозначного явного ACME email прежней конфигурации. Существующие
IP/domain issuer не меняются; TLS-проверка остаётся строгой, ожидание увеличено
до пяти минут. Тест Caddy проверяет разделение политик сайта, IP и домена
сотрудников без запросов сертификатов в CI. Наличие реального сертификата
и доступ из пользовательского браузера проверяются только после запуска на RU.
