# Уведомления клиентского кабинета

Изменения заявки и переписка сохраняются в базе независимо от внешней доставки.
Публичные события доступны клиенту в карточке заявки. Push не является единственным
источником сведений о заказе.

`client_notifications` — отдельная клиентская очередь. Она не использует подписки
сотрудников. Уникальный `event_id` защищает постановку одного события от дублей.
Миграция `20261105154000_client_notification_leases.sql` добавляет временную аренду
строки и время подтверждённой доставки без изменения старых таблиц и финансов.

`server/notifications.cjs` реализует ограниченный проход очереди и необязательный
останавливаемый цикл. Один проход по умолчанию обрабатывает до 20 строк. В короткой
транзакции `FOR UPDATE SKIP LOCKED` резервирует одну строку; доставка выполняется
вне транзакции. По умолчанию тайм-аут — 10 секунд, аренда — 45 секунд. Запись результата
возможна только при совпадении токена аренды. Просроченную аренду подхватывает другой
проход. Параллельные циклы не блокируют сохранение заявки на время доставки.

Повторы выполняются через 15, 30, 60, 120 секунд с ограничением задержки 15 минут.
Всего по умолчанию пять попыток. Исчерпанные записи остаются `failed`; они не
удаляются и не называются доставленными. После устранения ошибки оператор может
адресно вернуть нужные записи в очередь; автоматического массового сброса нет.
Логи содержат только статус, номер попытки и фиксированный код ошибки. Текст ошибки
провайдера, получатель, телефон, токен и содержание сообщения не журналируются.

Повтор после сбоя между доставкой и записью результата использует неизменный ключ
`client-event:<event_id>`. Будущий production-провайдер обязан обеспечивать
долговременную идемпотентность по этому ключу. Без этой гарантии worker отклоняет
адаптер. Один лишь lease не обеспечивает ровно одну внешнюю доставку при падении
процесса; это ограничение явно входит в контракт адаптера.

Общие сообщения компании не связаны с заявкой и могут не иметь `event_id`.
Для них используется уникальный неизменный ключ `client-notification:<id>` и
нейтральный текст без содержимого переписки. Сбой на последней разрешённой попытке
после истечения аренды явно помечается `DELIVERY_UNCONFIRMED`, а не остаётся
недоступной для обработки записью `pending`.

## Изолированная проверка

`createLocalNotificationTransport` принимает только `test`/`staging`, явный
`isolated:true` и абсолютный приватный каталог. Он не выполняет сетевых запросов:
создаёт атомарный файл в `privateDir/notifications` с правами 0600. Повтор с тем же
ключом и содержимым использует существующий файл. Разные данные с тем же ключом
вызывают ошибку. `sent` с этим адаптером означает только запись в тестовый outbox,
а не реальный push. `createSuppressedNotificationTransport` явно отмечает тестовую
доставку как `suppressed` и также запрещён в production.

Production-провайдер push не подключён и не проверен. Без адаптера worker записывает
`TRANSPORT_UNCONFIGURED`, сохраняет событие и планирует повтор; успешного ответа
доставки он не имитирует. Тестовый адаптер в production возвращает `UNSAFE_TRANSPORT`
до вызова транспорта. Реальные подписки сотрудников и клиентов не используются.

## Проверки

`client-portal/tests/notifications.test.cjs` использует настоящую изолированную
PostgreSQL-модель PGlite: постановка через триггер заявки, повторы, ограничение
попыток, параллельные workers, тайм-аут, восстановление просроченной аренды,
отказ устаревшей аренды, приватный атомарный outbox и отсутствие потери заказа
при ошибке уведомления. Внешняя доставка во всех проверках — тестовый транспорт.
