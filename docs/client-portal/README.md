# Клиентский кабинет «Домашний мастер»

Изолированная версия с настоящим сохраняющим данные API. Production не изменён.
База разработки: `390fff76ebc1932f056c384c2ddd165153bfed00`, а не отстающий `main`.

## Локальный просмотр

Требуется Node 24 и зависимости корневого проекта. Для декодирования фотографий
нужен `sharp` из зависимостей `client-portal`; в среде разработки использован
установленный runtime `sharp`. Обычная подготовка после checkout:

```sh
npm ci
```

```sh
npm install --prefix client-portal
```

```sh
npm run dev
```

Открыть `http://127.0.0.1:4180/client/` для клиента и
`http://127.0.0.1:4180/staff/` для сотрудника. Это локальные адреса, не публичный
preview. Инициализатор отказывается работать в непустой чужой БД и не обращается
к рабочим интеграциям. База и приватные файлы находятся в игнорируемом Git
каталоге `.client-portal-stage`. Не удалять его для обычного перезапуска.

Сначала запросить код в форме клиента. Затем в **отдельном локальном терминале**:

```sh
node client-portal/staging/access.cjs
```

Команда показывает последний неистёкший код или сгенерированный вход сотрудника
только в интерактивном терминале. Она не работает через HTTP и не выводит
секреты при перенаправлении stdout. Паролей и кодов в документации нет.
Каждый новый изолированный каталог получает собственные случайные секреты.

В управляемой среде разработки preview запускается её штатным daemon; он
использует другой внутренний адрес. Доступность этого адреса конечному
пользователю не подтверждена. Код не публиковался в сторонний хостинг.

## Как пройти рабочий сценарий

1. Клиент открывает услуги, выбирает количество или описывает нестандартную
   задачу, вводит адрес и пожелание по времени. Перед отправкой подтверждает
   телефон и читает тестовые документы. Реальный прайс ещё не утверждён:
   исходные услуги показывают «После уточнения».
2. В обычном приложении сотрудника появляется та же запись `orders` с
   источником «Кабинет клиента». Кнопка клиентского кабинета открывает
   переписку, фотографии, обращения, смету и подтверждение визита.
3. Владелец или руководитель управляет каталогом; диспетчер не может менять
   каталог. Цена вычисляется сервером; старая заявка хранит свой снимок.
4. Сотрудник назначает мастера и подтверждает время; пожелание клиента само
   по себе не подтверждает визит. Публичная карточка мастера настраивается
   отдельно и не содержит его личного телефона.
5. Сотрудник отправляет версию сметы. Клиент подтверждает именно эту версию.
   Изменение стоимости обычным интерфейсом сотрудников помечает ранее
   согласованную смету как требующую пересогласования.
6. Сообщения, обращения и фотографии сохраняются. Перенос и отмена сначала
   поступают на рассмотрение компании. Гарантийное обращение не создаёт
   новый оплачиваемый заказ и не начисляет зарплату повторно.
7. Мастер выполняет существующий процесс работ и отчёта. После приёма
   отчёта результат отображается в истории клиента.

## Архитектура и границы

- `client-portal/public/` — отдельная точка входа `/client/`, собственный
  manifest/service worker. Служебное приложение туда не загружается.
- `client-portal/server/` — отдельный Node API `/client-api/`, PostgreSQL
  в production, сохраняющий PostgreSQL/PGlite в изолированной разработке.
- Клиенты — отдельные `client_accounts`; регистрация не использует
  `auth.users` и не создаёт `business_staff`/`profiles`.
- Клиентские сессии — случайные отзываемые HttpOnly cookies. Они не являются
  действующими токенами внутреннего API. Производственный origin требует HTTPS.
- Заявки — существующие `orders` и `work_items`; связь с клиентом необязательна
  для старых строк. Для старой истории нужна проверка конкретной заявки
  сотрудником, записанная в журнал. Совпадение телефона ничего не открывает.
- Существующие формулы `order-payroll.js` и финансовые снимки сохранены.
  Прямые заказы используют уже имеющееся правило; Hands и Лемана не изменены.
- Внутренний начальный статус повторяет обычное создание сотрудником
  (`В работе`), чтобы старый триггер не очищал отчёт при первой отправке.
  Клиент видит отдельный понятный статус: заявка принята, мастер подбирается.
- `client-portal/staging/` — только изолированный launcher, синтетическая
  схема и адаптер Supabase-запросов к настоящему SQL. Исполняются текущие
  Edge handlers и проверенные миграции защитных триггеров. Это реконструкция
  контрактов из репозитория, не копия обследованной рабочей БД.
- SMS — приватный тестовый outbox; файловое хранилище — отдельный приватный
  каталог; Google Drive в сквозном тесте заменён локальным файловым архивом.
  Cron, вебхуки и реальные доставки не запускаются.
- `client-portal-staff.js` выключен по умолчанию; staging включает его
  конфигурацией. Его можно отключить независимо от внутреннего приложения.
