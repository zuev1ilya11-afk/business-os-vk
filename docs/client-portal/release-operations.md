# Эксплуатация и граница выпуска

05.11.2026. Документ относится к новому клиентскому кабинету.
Он не разрешает изменение production. Команда владельца для выпуска:
«Тестовую версию проверил, разрешаю публикацию».

## Разделение сред

Из корня репозитория после установки зависимостей:

```sh
npm run dev
```

Та же точка входа без npm:

```sh
node client-portal/staging/start.cjs
```

Локальные адреса: `http://127.0.0.1:4180/client/` и
`http://127.0.0.1:4180/staff/`. Это loopback, не публичные ссылки.
Launcher сохраняет БД и приватные файлы в `.client-portal-stage/`; случайные
учётные данные и тестовые OTP доступны только в приватных локальных файлах,
не выводятся в консоль и не включаются в репозиторий/архив выпуска.
Остановка — SIGINT/SIGTERM с закрытием HTTP listener и БД.
`NODE_ENV=production` запрещает запуск staging launcher.

В `client-portal/server/api.cjs` экспортируется
`createPortal({db,config})` с обработчиком `handle(Request)`.
`client-portal/staging/integrated.cjs` соединяет этот обработчик с настоящими
существующими Edge handlers сотрудников и отдельной синтетической БД.
Заглушкой является внешний транспорт архивирования/доставки; это не тест
реальных Google Drive, SMS, push и сторонних кабинетов.

Тестовая среда использует синтетические данные и отдельное сохраняемое
хранилище. Её OTP-транспорт, сессии, сотрудники, файлы, задания и уведомления
не должны использовать production credentials или реальные каналы доставки.
Нельзя запускать пример seed/migration bootstrap на действующей БД.

Для production выделяются отдельная точка входа, API и host-only сессии
клиента. Внутренний адрес сотрудников сохраняется. Новые таблицы добавляются
к бизнес-модели; действующие заявки и финансовые снимки не пересоздаются.
Перед запуском проверяются фактические типы/ограничения `orders`, работ,
ролей и session API, а также регистрационные триггеры на действующей БД.
Сверка только с репозиторием эту проверку не заменяет.

## Контрольный пакет

`client-portal/ops/build_release.py` создаёт ZIP из **закоммиченного** изменения
от сохранённой базы `390fff7`. В пакете:

- `manifest.json`: commit, base, SHA-256 каждого файла, старый SHA для
  существующих файлов и явный `production_authorized=false`;
- `candidate/`: новые версии изменённых файлов;
- `source.patch`: полный проверяемый diff.

Пакет не содержит установщика, который автоматически заменяет текущий RU
runtime, и не выполняет SQL. Обновление файла, существующего на RU, разрешено
только после сравнения живой версии и адресного переноса изменения.
Файлы окружения с секретами, runtime БД, приватные загрузки и логи запрещены
в пакете. Скрипт отказывает при незакоммиченных tracked changes,
удалениях/переименованиях и попытке перезаписать существующий архив.

Сборка из корня репозитория, выходной архив вне worktree:

```sh
cd client-portal/ops
```

```sh
python3 build_release.py --output /tmp/portal-release.zip
```

Проверка инструментов:

```sh
python3 -m unittest discover -s . -p test_ops.py
```

Это пакет кандидата на выпуск, не подтверждение совместимости с текущим
сервером и не standalone backup существующей системы.

## Последовательность безопасного выпуска

1. Зафиксировать текущую публикацию, mounts, маршруты, конфигурацию без
   секретов и фактические хеши затрагиваемых web/API файлов. Сверить runtime
   с baseline. Не использовать main как замену всей серверной папки.
2. Выполнить read-only сбор CPU/RAM/swap/дисков, ограничений/перезапусков
   контейнеров и размера БД/Storage; изучить доступную историю нагрузок.
   Не размещать второй тяжёлый стек без измеренного запаса.
3. Получить новую согласованную копию PostgreSQL, файлов и конфигурации
   в приватное место на российской инфраструктуре. Зафиксировать размер,
   время и хеш; проверить свободное место до копирования.
4. Восстановить эту копию в изолированное окружение с запрещёнными внешними
   доставками и фоновыми задачами. Проверить количество таблиц/строк,
   ограничения, чтение выбранных фотографий/актов и вход тестового сотрудника.
   Не открывать реальные персональные данные в публичном preview.
5. Сравнить пять добавочных клиентских миграций с реальной схемой. Применить их по timestamp-порядку
   сначала к восстановленной копии с ограниченными lock/statement timeout.
   Проверить rollback транзакции при ошибке и совместимость старого приложения.
6. Запустить API/клиент отдельно с production guards; подтвердить отсутствие
   тестового OTP, явную настройку SMS-бюджета, согласия с настоящими реквизитами,
   приватные загрузки и отсутствие регистрации клиента в business_staff.
7. Пройти сценарий клиент → диспетчер → мастер → отчёт → история, изоляцию
   двух клиентов, повтор запросов, смету/перенос/отмену, сохранность финансов.
   Проверить существующие авторизацию, отчёты, акты и XLSX без изменения формул.
8. Передать владельцу точный commit, тесты, ограничения и затрагиваемые сервисы.
   Только после отдельной команды выпуска получить свежую backup и повторить
   read-only preflight, чтобы обнаружить изменения после тестирования.
9. Применить согласованную добавочную миграцию и включить клиентский API/PWA
   отдельным маршрутом. DNS/порты/маршрутизация согласуются отдельно; настройки
   приложения сотрудников не заменяются целиком.
10. Выполнить контрольные проверки и наблюдение за ошибками/ресурсами.
    Остановить включение при расхождении любой проверки; не лечить проблему
    сбросом БД или возвратом старой БД поверх новых заказов.

Шаги 1–9, затрагивающие RU, в текущей среде **не выполнены**. Доступа к RU
и свежей восстановленной копии нет. Последовательность не является заявлением
об успешной выкладке или готовности сервера к заданной нагрузке.

## Независимое отключение и совместимый откат

При инциденте сначала отключается **только новый клиентский вход/API**.
Сотрудники продолжают использовать существующий адрес и API.
Отдельные очереди клиентских уведомлений приостанавливаются без удаления;
сохранённые заявки остаются в общей таблице.

Откат приложения возвращает только файлы/конфигурацию данного выпуска,
после проверки, что с момента установки их не менял другой выпуск.
Клиентские аккаунты, заявки, переписка, согласия, вложения и финансовые снимки
не удаляются. Автоматической down-миграции с DROP нет.
Старая версия сотрудников должна быть проверена с добавленной схемой заранее.
Если откат сохраняет старый дефект, клиентский вход остаётся отключённым
до исправления; повторно выполненные заявки не начисляются заново.

## Выполненная репетиция восстановления

`client-portal/tests/restore.test.cjs` прошёл 05.11.2026 (1/1, около 7 секунд).
Тест через настоящий клиентский API регистрирует синтетический аккаунт,
создаёт заявку, сообщение и фотографию, затем **полностью закрывает PGlite**.
БД и приватные файлы копируются в другой временный каталог с правами
0700 на каталоги и 0600 на файлы; новая среда открывается из этой копии.

Проверены совпадение количества и хешей записей в 11 таблицах, сохранение
версий согласий, сессии, idempotency, уведомлений и сотрудников; повторное
чтение заявки/переписки через API; доступ к фотографии и совпадение её байтов.
Секреты и коды в результат теста не выводятся. Временные данные удаляются
после закрытия обеих сред.

```sh
node --test client-portal/tests/restore.test.cjs
```

Это успешное восстановление **синтетической локальной PGlite-среды**.
Настоящие PostgreSQL backup, Storage и конфигурация RU не читались и не
восстанавливались. Их проверка остаётся обязательной до production.

## Мониторинг

`client-portal/ops/monitoring.rules.yml` — подготовленный шаблон Prometheus:
доступность клиентского/внутреннего API, RAM, CPU, диск и будущие метрики
ошибок доставки/застрявших заданий. Пороговые значения — начальные настройки
для staging, не подтверждённые пределы рабочего сервера.

Шаблон не содержит адресов production и получателей уведомлений. Он не
подключён к работающему мониторингу. Сначала нужно настроить отдельные jobs,
node exporter/health probes и реальные имена метрик приложения; затем
проверить исчезновение/восстановление тестового API и сбой тестовой доставки.
Метрики ошибок доставки нельзя считать действующими, пока exporter их не
публикует. Секреты, номера телефонов, адреса и тексты сообщений в labels/logs
не включаются. Подключение внешнего платного сервиса отдельно согласуется.

## Нагрузочная проверка

Нагрузка разрешена только на изолированной среде. Протокол результата должен
содержать commit, тип БД, CPU/RAM, число клиентов/параллельных запросов,
длительность, число операций, p50/p95/max, ошибки, CPU/RAM/диск до и после.
Проверяются каталог, собственные заявки с пагинацией, создание, сообщения
и загрузки. Повтор запроса проверяется отдельно от новых операций.

PGlite/локальный тест не заменяет испытание PostgreSQL и HTTP-стека на RU.
Из результатов локального теста нельзя вывести поддерживаемое число реальных
клиентов. Тест на общем production-хосте запрещён без доказанной изоляции
и лимитов ресурсов.
