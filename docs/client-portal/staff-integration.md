# Интеграция кабинета клиента с сотрудниками

Модуль `client-portal-staff.js` подключается последним в shell, но ничего не меняет
и не выполняет запросов, пока `BOS_CLIENT_PORTAL_CONFIG.enabled` не равен `true`.
Изолированный запуск устанавливает этот флаг. Production-включение — отдельный
шаг выпуска после проверки совместимости текущего сервера. Отключение флага
убирает новый интерфейс без удаления заявок и клиентских данных.

`apiBase` должен быть `/client-api/` на том же origin. Отправлять сессию сотрудника
на другой хост модуль отказывается. Он использует существующий `x-bos-session`,
не клиентскую cookie. Сервер проверяет активность сотрудника и разрешённую роль.

## Для диспетчера

1. Клиентская заявка появляется в обычном списке с источником «Кабинет клиента».
   Фильтр источников уже формируется из фактических заявок. В БД это та же строка
   `orders`, не копия; обычная карточка и отчёт мастера остаются основным процессом.
2. Кнопка «Кабинет клиента · сообщения и заявки» доступна на главной, в заявках и
   графике. В карточке связанной заявки есть отдельный вход в переписку.
3. Назначить мастера можно в прежней карточке. Клиентская панель также позволяет
   назначить мастера и явно подтвердить дату/время. Пожелание клиента показано
   отдельно и само по себе не считается визитом.
4. В смете вводятся позиции, количество и цена за единицу. Итог считает сервер.
   Каждая отправка создаёт новую версию; клиент принимает конкретную версию.
5. Ответ в блоке «Переписка с клиентом» виден клиенту. Внутренние комментарии
   обычной заявки автоматически в эту переписку не переносятся.
   Можно приложить фотографии JPEG/PNG/WebP до 5 МБ. Загрузка начинается после
   отправки; у каждого файла есть отдельный результат. При ошибке сообщение
   не отправляется, успешно загруженные файлы сохраняются для повторной попытки.
   Повтор использует те же идентификаторы загрузок и сообщения. Фото читаются
   через авторизованный staff endpoint; просмотр не закрывает черновик переписки.
6. Кнопка «Обращения» открывает переносы, отмены, гарантийные и обращения по
   персональным данным. Принятый перенос требует отдельного согласования визита.
   Гарантийное обращение не создаёт новую оплачиваемую заявку.
7. При ручной привязке старой заявки сотрудник выбирает существующий клиентский
   аккаунт, указывает конкретный внутренний ID заявки и основание проверки.
   Массового поиска старой истории по совпадению номера телефона нет.

## Для владельца и руководителя

«Каталог услуг» позволяет добавлять и редактировать категории, описание, единицы,
тип цены, стоимость, условия и доступность. Цена не публикуется как подтверждённая
без явной отметки; для неподтверждённых цен есть «После уточнения» и черновик.
Исторические снимки заказов не изменяются при обновлении каталога.

«Карточки мастеров» задаёт публичное имя, специализацию и фото. Личный телефон
мастера в клиентский интерфейс не публикуется.

## Финансовая совместимость

Действующий `order-payroll.js` уже относит именованный источник `client_portal`
к прямым заказам: мастер 60%, компания 40%. Формулы не изменены. Сохранённые
начисления принятых отчётов, включая нулевые, сохраняются. Источники Hands/Руки и
Лемана Про продолжают использовать свои прежние правила.

## Проверки

`tests/client-portal-staff.test.cjs`: расчёт прямых заказов и сохранённых снимков,
оригинальные обработчики bootstrap/назначения с одним идентификатором заявки,
ограничение мастера своей заявкой, отсутствие эффектов при выключенном флаге,
отказ от отправки сессии на другой origin. Edge-обработчики исполняются в тесте;
их транспорт БД в этом наборе — fixture, не реальная внешняя интеграция.

`tests/client-portal-staff.spec.js`: исходный интерфейс сотрудников и изолированные
ответы клиентского API; экранирование пользовательского текста, отправка ответа,
поля каталога, версия сметы и узкая ширина. Этот набор проверяет UI-контракт;
сквозная проверка с настоящей локальной БД описывается отдельно в общем отчёте.
