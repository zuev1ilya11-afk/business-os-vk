# Исправление возврата заявки после отправки отчёта

## Основание и границы

Ветка `fix/master-report-submit-reset`, база `390fff7` (`fix/master-export-claims-20261031`).
`origin/main` на начало работы — `80a97b3`, 22 октября; более поздние исправления
отчётов, даты поступления, финансов и рекламаций находятся в отдельных ветках.
Поэтому использовать полный `main` для замены рабочей версии нельзя.

Старая локальная копия `/workspace/scratch/0d7a8daa67b9/business-os-vk` содержит
исходники, но её `.git` указывает на отсутствующий worktree. Её файлы не изменялись.
Создана отдельная копия существующего репозитория с историей и отдельная ветка.
Изменения этой задачи не включают сайт или клиентский кабинет.

Production, реальные заявки, секреты и подписки не изменялись. Доступа к рабочей
БД/серверному runtime и учётным записям сотрудников в этой сессии нет. Воспроизведение
доказано для кода репозитория и сохранённого SQL; соответствие установленного
серверного триггера проверяется отдельным read-only preflight. Список реально
пострадавших заявок пока не установлен.

## Подтверждённая причина

`master-workflow-api` сохраняет этапы выезда и начала работы отдельно от общего
статуса. Например, импортированная/назначенная заявка может оставаться
`status='Назначена'`, хотя мастер уже дошёл до `master_workflow_stage='started'`.
Оба обработчика финализации отчёта записывают `status='В работе'`,
`report_review_status='pending'`, токен и ссылки на вложения одним UPDATE.

`guard_order_completion()` из миграции `20261004100840_manual_order_completion.sql`
считает **любой** переход из другого статуса в «В работе» началом нового цикла.
BEFORE UPDATE в том же запросе стирает отчёт и сбрасывает этапы. Это случай Г
из задания: перезапись происходит внутри исходного UPDATE, ещё до его ответа.
Дополнительно API и UI не проверяли сохранённую квитанцию и сообщали об успехе.
Исходный API из `390fff7` исполнен отдельно: HTTP 200 / ok:true и одновременно
пустые поля отчёта в ответе и PostgreSQL. Снимки: `docs/evidence/report-submit-reset/before.json` и `after.json`.
Экран тестового мастера: `docs/evidence/report-submit-reset/master-pending.png`.
После исправления загрузка акта/фото, финализация, повторное чтение мастером
и приёмка менеджером отвечают HTTP 200 с согласованным состоянием PostgreSQL.

| Условие | До UPDATE | Результат старого триггера | После исправления |
|---|---|---|---|
| Общий статус | Новая / Назначена | В работе | В работе |
| Этап мастера | started | assigned | started |
| Договорённость | сохранена | master_agreed_at = NULL | сохранена |
| Состояние отчёта | not_submitted | not_submitted | pending |
| Токен и дата отправки | новые в UPDATE | NULL | сохранены |
| Ссылки на акт и фото | новые в UPDATE | NULL / [] | сохранены |
| Ответ API | — | прежде ok:true; теперь REPORT_NOT_SAVED при старом SQL | ok:true с квитанцией |

При исходном «В работе» старый триггер отчёт не стирает. Это объясняет зависимость
сбоя от состояния заявки. Домен/порт не требуются для воспроизведения и не объявлены
причиной. Сетевые маршруты приложения не изменены.

В воспроизведённом сбое файлы загружаются в Storage, но их ссылки, токен и дата
отправки в `orders` теряются. Это **не** сохранённый отчёт, доступный менеджеру.
Наличие объектов в Storage само по себе не доказывает успешную финализацию.
Установить сохранность конкретных рабочих файлов можно только чтением сервера.

## Изменения

- Новая миграция `20261110140000_preserve_submitted_report.sql` заменяет только
  функцию существующего триггера. Валидная новая отправка из незакрытой заявки
  выделена из условия перезапуска цикла. Условия сброса при отказе/повторном
  открытии закрытой заявки, запрет завершения без отчёта и исключение ручного
  завершения руководителем сохранены. Исторические строки не обновляются.
- `order-lifecycle-api/index.ts` и обе ветки `report-api/index.ts` проверяют
  возвращённый триггером токен/дату/состояние. При утрате отчёта — HTTP 409
  `REPORT_NOT_SAVED`, а не подтверждение успеха.
- `report-chunk-upload-v23.js` проверяет квитанцию ответа до закрытия формы и
  обновления карточки. При неподтверждённом/неопределённом результате использует
  существующее авторизованное повторное чтение; сохраняет файлы и ввод формы.
- Пересобраны штатные `startup-shell.bundle.js`, `build-version.js`, `index.html`,
  `sw.js`. Дизайн, формулы выплат, роли/RLS, маршруты API и схема отчёта не менялись.

Транспортная регрессия отдельно выявила обход сверки при HTTP 500: загрузчик
переходил к другому endpoint до обработки неопределённого результата. Для
финализации ошибка должна сразу возвращаться существующему механизму сверки;
повтор загрузки отдельного файла остаётся прежним. Правка применена и проверена:
HTTP 500 после коммита приводит к свежему чтению, не ко второй финализации.

Идемпотентность основана на существующем серверном условном UPDATE и квитанции
токена. Новые проверки исполняют его на PostgreSQL: два параллельных запроса
получают одну сохранённую квитанцию; повтор после приёмки не меняет её. Формула
невыполненных работ использует `original_amount`, повтор не вычитает сумму снова.
Незавершённая загрузка может оставить неиспользуемый объект Storage — прежнее
поведение; исправление не удаляет такие объекты и не перезаписывает прикреплённые.

## Проверки и реальные условия

Тестовые сессии подписаны отдельным тестовым секретом и имеют роли `master` и
`manager`; режим просмотра владельцем не используется для проверки мастера.
Исполняются настоящие TypeScript-обработчики через существующий VM harness.
Для новой регрессии таблица orders, условные UPDATE и триггер исполняются в
PGlite 0.5.10 / PostgreSQL 18.6 (WASM); прочие таблицы, Storage и Google Drive — тестовые адаптеры.
Браузерный HTTP проходит через Playwright routes, не через production/Deno gateway.

- Воспроизведено стирание отчёта старым SQL при Новая/Назначена.
- Проверены оба финализатора, все три активных исходных статуса, сохранность
  договора/назначения/работ/выплаты, одновременный запрос и повтор после приёмки.
- Полный UI: назначенная заявка → выезд → начало → акт/фото → отправка → ожидание
  проверки → reload → новая сессия мастера → просмотр вложений менеджером → приёмка.
- Ошибка загрузки, ошибка сохранения, ложный ok:true, потеря ответа после коммита,
  двойная отправка/сброс общего busy: данные сохраняются, повтор не создаёт новую
  финализацию. Имеющиеся тесты проверяют запрет повтора при неудачном свежем чтении.
- Старая SQL-проверка ручного завершения и прав выполнена с новым триггером.
- Проверка рекламации исполняет новый триггер вместе с финансовыми snapshot-
  триггерами: первоначальное начисление остаётся одно, исходная дата не меняется.
- Установщик/откат проверены на SQL: неизвестная версия функции отклоняется,
  повторный несогласованный откат отклоняется, строки orders не изменяются.

Общий UI-прогон **не был полностью зелёным с первой попытки**. Ошибки навигации,
компактной карточки, прогресса, справки, панели владельца, регистрации и диспетчера
прошли при отдельном повторе с одним worker и увеличенным общим timeout.
В тесте удаления расхода `toContainText('0')` совпадает и с предыдущим значением
200, поэтому проверка массива может опережать завершение удаления. Эта проверка
прошла на неизменённой базе 390fff7 и затем на финальном коде; код финансов и этот
тест не изменялись. Это ограничение стабильности общего набора, не скрытая ошибка.

Финальные 27 UI включают 20 проверок отчётов и 7 проверок расходов. В новом полном
сценарии менеджер нажимает «Открыть акт» и миниатюру фото, проверяется загрузка
изображений и ссылка на оригинал; простая проверка наличия URL этим не подменяется.
При ошибке дополнительно проверяются сохранность описания и суммы допработы и
их фактическое сохранение после повторной попытки.

Команды целевой регрессии (для разработчика, не серверной консоли):

```sh
node --test --test-concurrency=1 tests/master-report-reset.test.cjs tests/report-submit-release.test.cjs tests/claim-accruals-sql.test.cjs tests/report-submit-reset-network.test.cjs
```

Playwright запускался штатным набором тестов с отдельным временным config: тот же
локальный web server и сетевые ограничения проекта, установленный соответствующий
Playwright headless shell Chromium, внешние HTTP endpoints — только тестовые routes.

Deno 2.9.6 typecheck двух изменённых функций прошёл на точных копиях исходников
с локально установленным @supabase/supabase-js 2.119.0, без изменения зависимостей проекта.
Прямое скачивание зависимости самим Deno было недоступно; npm получил тот же пакет
через штатную сеть. Проверка использовала --node-modules-dir=manual --no-lock.
На серверной PostgreSQL 17.x эта миграция пока не исполнялась.
На реальном сервере пока не проверены: текущий код функции, настоящие файлы
Storage/Google Drive, фактические push-уведомления, устройства iOS/Android и
исторические заявки. Нет утверждения об exactly-once работе внешнего Drive.

## Проверка и адресное восстановление рабочих данных

`deploy/report-submit/check.sql` выполняется в READ ONLY. Выводит только технические
ID/статусы/даты/булевы признаки и сведения о триггере. Результат — кандидаты на
проверку, не автоматически подтверждённые повреждения. Он не выводит телефоны,
адреса, токены, ссылки или содержимое вложений. Пустая выборка не исключает сбой:
старый триггер мог полностью очистить признаки отправки.

Для каждого кандидата отдельно:

1. Сопоставить точный order_id с журналом запросов, резервной копией до сбоя и
   метаданными Storage `orders/<id>/<upload_token>/`. Никаких массовых догадок по
   времени файла или по одному флагу `assigned`.
2. Подтвердить набор акта/фотографий, токен отправки, состав работ, договорённость,
   назначение и наличие/отсутствие последующей приёмки/рекламации.
3. Если отчёт сохранён и повреждён только этап — менять лишь подтверждённые
   поля этапа. Если ссылки потеряны — готовить точечное восстановление из
   подтверждённого комплекта; не вызывать отправку отчёта повторно.
4. Перед записью повторно прочитать строку под блокировкой, проверить id,
   updated_at, status, master_staff_id, report_upload_token, report_uploaded_at,
   report_review_status и снимок начисления. При расхождении прекратить операцию.
5. Сохранить приватный снимок строки до изменения, выполнить только согласованный
   UPDATE по одной заявке в транзакции, проверить вложения и видимость обеим ролям.
   Не менять суммы, оплату, финансовые snapshots и существующую приёмку.

Скрипта массового восстановления нет. До получения достоверной истории точный
UPDATE для рабочей заявки не сформирован и не выполняется.

## Передача и публикация

Исправление сохранено локальными коммитами в `fix/master-report-submit-reset`.
Первоначальная отправка ветки в GitHub была отклонена автоматической проверкой:
требовалось явное разрешение на удалённую публикацию исходников. Пользователь
затем разрешил отправку подготовленной ветки. Разрешение не распространяется на
слияние или обновление production; передача оформляется отдельным draft PR.

Пакет подготовлен для серверной проверки и согласованной установки, но это не
утверждение об успешной проверке на действующем runtime. Перед публикацией нужно
сопоставить реальный триггер/код с базой правки и пройти изолированный серверный
сценарий. Исходный main отстаёт от использованной базы; полный откат/замена на main
недопустимы. Процедуры: `deploy/report-submit/README.md` и `database.py`.
Откат SQL возвращает точную сохранённую функцию; API/frontend — сохранённые перед
развёртыванием версии. Данные отчётов и начисления откатом не удаляются.
