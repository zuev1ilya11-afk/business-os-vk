# Ручное завершение заявки

Действие доступно существующим активным ролям `owner` и `manager`. Диспетчер и мастер не получают его ни в карточке, ни через API. Отменённые заявки не закрываются этим действием.

`order-lifecycle-api/manualCompleteOrder` использует обычную проверку BOS-сессии и вызывает `bos_manual_complete_order`. RPC доступен только `service_role`, повторно проверяет роль сотрудника, блокирует строку заявки и сверяет `expected_updated_at`. Уже выполненная заявка возвращается без UPDATE: повтор не меняет дату, аудит и не запускает триггеры повторно.

Изменяются только обычный статус `Выполнена`, `completed_at`, `sync_status` и append-only `manual_completion_history`. Остаются прежними суммы и выплаты, фактические этапы работы и все поля настоящего отчёта. Для текущего ручного завершения интерфейс читает сохранённую выплату, включая ноль, без нового расчёта.

У текущих bigint-заявок нет совместимого неизменяемого журнала. Поэтому миграция добавляет JSONB-поле в существующую таблицу, без новой таблицы или роли. Оно хранит имя, идентификатор и роль сотрудника на момент события, время и обязательную причину. Обычные записи через API не могут менять журнал. При разрешённом штатном повторном открытии история сохраняется.

Существующий `guard_order_completion` сохраняет все штатные проверки и сбросы. Исключение для отсутствующего отчёта действует только внутри защищённой транзакции ручного завершения. Прямые обычные UPDATE по-прежнему требуют отчёт. Реальный ожидающий проверки отчёт остаётся ожидающим; его последующий приём использует штатное архивирование и сохраняет первоначальную дату ручного закрытия.

Поля `report_review_status` и `report_upload_token` не входят в UPDATE ручного завершения, поэтому триггер постановки отчёта Hands в очередь не срабатывает. Формулы Hands, 60/40, удержания и выплаты не изменены.

При потере ответа интерфейс читает состояние заявки до повтора. Если проверить его не удалось, повторное завершение заблокировано до успешной проверки. Изменившаяся версия требует заново открыть карточку.

Проверки: `tests/manual-completion.test.cjs`, `tests/manual-completion.spec.js`, `scripts/test-manual-completion.sh` (включён в PostgreSQL-gate). SQL-тесты выполняются только в явно указанной одноразовой базе; два отдельных соединения проверяют одновременное завершение.

Порядок публикации: миграция, `order-lifecycle-api`, `mini-app-api` с обновлённым общим читателем `order-payroll.js`, затем frontend. Пользовательские заявки не завершаются для проверки deployment.
