# Безопасная подготовка staging

Полный статус и ограничения: [AUDIT.md](AUDIT.md). Результаты: [VERIFICATION.md](VERIFICATION.md).

**Это подготовка и локальные репетиции. Доступного серверного «пузыря» пока нет.**

## Следующий шаг на сервере: только чтение

Скопировать `deploy/staging/inventory.py` на сервер как `/tmp/bos-staging-inventory.py`, затем выполнить одну короткую команду:

```sh
python3 /tmp/bos-staging-inventory.py
```

Она перечислит все Docker-контейнеры (включая остановленные), образы, порты, сети, mounts, найденные frontend BUILD_ID и свободные ресурсы. Значения env, команды контейнеров и содержимое БД не печатаются. Ничего не изменяется. Не присылать `.env`, пароли, токены или полный `docker inspect`.

Для последующей проверки сохранить этот безопасный вывод в приватный файл (меняется только новый файл отчёта):

```sh
umask 077
```

```sh
python3 /tmp/bos-staging-inventory.py > /tmp/production-inventory.json
```

Отдельно проверить вне-Docker процессы и host timers; не считать Docker-инвентаризацию их полным списком. Затем определить верный live frontend и состав серверных исправлений. Любые изменения общего reverse proxy, DNS, TLS или firewall — отдельный согласуемый шаг. Недостаток RAM/диска не компенсировать за счёт production.

## Что требуется для настоящего запуска

1. Текущая инвентаризация и сравнение live BUILD_ID/хешей с выбранным SHA. Не считать `main` работающей версией.
2. Полная проверенная schema-only основа БД, включая RLS, роли, функции, триггеры, очереди и расширения; никаких клиентских строк/секретов.
3. Зафиксированные image digests реально используемых PostgreSQL/REST/Auth/Storage/Edge/proxy; проверить, что internal network не требует скачивания импортов во время старта.
4. Отдельный Compose project, приватный root, volumes, internal networks, loopback-порт, новые credentials/подписи и тестовые аккаунты. Рабочие bind mounts и внешние secrets запрещены.
5. Единственный тестовый public origin во всех API, callback и file URL; production fallback должен завершаться ошибкой. Защита входа сохраняется, реальные RLS не отключаются.
6. Серверный запрет внешнего egress для всех сервисов, включая SQL pg_net; отключённые SQL/host cron, workers, email/SMS/push/импорт. Отдельный локальный приёмник отправок подключать только после проверки проекта/сети, не включать его как публичный proxy.
7. Через реальные тестовые аккаунты каждой роли выполнить все сценарии SPEC, включая загрузку файлов/оригиналы, ограничения мастера, перезапуск, сохранность данных и PWA.
8. Проверить полный backup PostgreSQL + Storage bytes/metadata + защищённая конфигурация и восстановить его в ещё одну пустую тестовую цель. Пройти A→B→контролируемый сбой→A на настоящем staging.

## Структурная проверка плана

После подготовки Compose сохранить его разрешённую конфигурацию локально в приватный файл. Вывод `docker compose config` может содержать секреты: его не публиковать и не присылать в чат.

```sh
umask 077
```

```sh
docker compose -f staging.compose.yml config --format json > /tmp/staging-plan.json
```

Короткие аргументы ниже относятся к файлам на том же сервере; `/opt/bos-staging-review` — пример **нового** приватного пути, а не обнаруженная конфигурация. Заменить после проверки инвентаризации.

```sh
python3 deploy/staging/guard.py \
  --environment staging \
  --compose-json /tmp/staging-plan.json \
  --production-inventory /tmp/production-inventory.json \
  --root /opt/bos-staging-review
```

Скрипт только читает файлы. Требует шесть явно названных сервисов `web`, `edge`, `db`, `auth`, `rest`, `storage`, внутренние сети, image digests, отдельные mounts/volumes, loopback ports, отключение опасных container capabilities. Неизвестные топологии сначала адаптировать и покрыть тестами. Отсутствие сервиса/неполный план не заменяется рабочими defaults.

Успех структурной проверки **не является разрешением на запуск**: обязательные переменные самих сервисов, schema bootstrap, уникальность секретов, защита входа и реальная маршрутизация проверяются отдельно. Скрипта автоматического `up` сейчас намеренно нет: фактическая инфраструктура не обследована.

## Локальные репетиции

Из корня этой ветки, с установленными зависимостями `package-lock.json`:

```sh
python3 -m unittest discover -s deploy/staging -p 'test_*.py'
```

```sh
node --test deploy/staging/test-data.cjs
```

Для сохранения результатов использовать новый путь на каждый запуск. Повторное использование существующей директории отклоняется.

```sh
python3 deploy/staging/rehearse.py \
  --environment staging \
  --workdir /tmp/bos-staging-rehearsal-01 --check
```

```sh
python3 deploy/staging/rehearse.py \
  --environment staging \
  --workdir /tmp/bos-staging-rehearsal-01
```

```sh
node deploy/staging/rehearse-data.cjs \
  --environment staging \
  --workdir /tmp/bos-staging-data-01
```

Репетиция frontend использует `install`/`rollback` существующего установщика. Версия B — искусственная локальная версия; **её не публиковать**. Восстановление данных использует холодную копию закрытой PGlite с частичной тестовой схемой. Это не команда резервного копирования живого PostgreSQL.

Данные создаются в новой пустой тестовой БД: девять заявок, работы с количеством, синтетические PNG/акт. Двойное заполнение проверяет отсутствие дублей. Сброс — запуск в новом пустом пути; автоматического удаления произвольной БД/директории нет. Никакие URL БД или production-пути CLI не принимает.

## Локальный макет мастера

```sh
npm run preview:master-order
```

Открыть `http://127.0.0.1:4176` на той же машине; остановка — Ctrl+C. Это прежний preview с реальным UI и тестовой сессией, не полноценные Auth/БД. Он содержит заметную тестовую отметку, принимает только loopback Host и same-origin запросы, блокирует внешние ресурсы CSP, не раздаёт внутренние JSON/документацию и Service Worker. Не публиковать через внешний туннель и не использовать для проверки реального входа.

CSP и перехват обычных ссылок не запрещают абсолютно все переходы верхнего уровня (`window.open`, изменение location, средняя кнопка мыши). Поэтому ручное открытие макета в обычном браузере не является доказательством полной сетевой изоляции. Автоматические проверки запускаются через блокирующий внешний трафик proxy; для ручной приёмки полного staging нужна такая же защита окружения.

Для регрессий этого этапа использовать существующий `scripts/qa/offline-playwright.config.cjs`, `BOS_TEST_OFFLINE=1` и `BOS_TEST_ARCHIVE_GAS=0`. Обычный общий UI-набор содержит внешний GAS health-тест; его здесь не запускать.

## Порядок будущего production-выпуска

1. Ветка → lockfile-зависимости → проверки/сборка → настоящий staging → полный smoke.
2. Зафиксировать source SHA, lockfile hash, состав frontend/backend, миграции (для этапа 0 их нет), BUILD_ID и хеши артефактов.
3. Получить отдельную команду владельца на production.
4. Повторно проверить live build, серверные исправления, свободное место, активные запросы/задания. При дрейфе остановиться.
5. Сделать и проверить защищённый backup БД, файлов и конфигурации; зафиксировать точку восстановления. Выбрать согласованное окно и метод консистентной копии DB/Storage.
6. Собрать production-артефакт **из того же SHA**, если адреса встраиваются при сборке. До публикации проверить отсутствие тестовых адресов/данных/секретов. Staging bundle целиком не переносить.
7. Применить соответствующий существующий защищённый установщик, адаптированный к подтверждённому live baseline. Предварительно `--check`, затем только после разрешения `--apply`.
8. Проверить build/asset hashes, входы, заявки, отчёт/акт/оригиналы, обновление страницы, финансы и PWA. Нельзя считать одну главную страницу успешным релизом.
9. При предусмотренном сбое откатить только файлы приложения по сохранённому журналу и проверить совместимость с БД. Сохранить заявки/изменения после backup.
10. Восстановление старой БД — отдельная аварийная процедура с оценкой потери данных, никогда автоматическое следствие обычного rollback.

Готовые исторические команды `--check`, `--apply`, `--rollback` находятся в [документации пакета даты](../../deploy/master-received-date/README.md). Они относятся только к тому выпуску, **не являются командой публикации этапа 0**. Универсальная команда обновления текущего сервера не подготовлена: её нельзя корректно составить без подтверждённого live baseline. В этой задаче никакие production-команды не выполнялись.
