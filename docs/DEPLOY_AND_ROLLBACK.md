# Публикация и откат подготовленных исправлений

## Текущее решение

**Production не изменён. Полный выпуск ветки пока заблокирован отсутствием подтверждённой RU версии.** Ветка аудита — проверяемые изменения исходников, а не готовый образ действующего сервера. Старые установщики проверяют точные хеши и не предназначены для произвольного нового bundle. Не обходить их проверки и не заменять сервер всем main/кандидатом.

Последний полный локальный UI-прогон зелёный (890/0/4), но предыдущий один раз выявил несохранение очищенного комментария (AUD-15). Причина не установлена; успешный повтор не считается исправлением. Этот сценарий обязательно проверить на соответствующем серверу стенде. CI точного выпуска должен быть зелёным.

## Состав

| Изменение | Затронутый runtime | БД / frontend / история |
| --- | --- | --- |
| Пустые данные файлов | `report-api`, `report-file-upload` | Новых миграций нет, история не меняется |
| Причина возврата | `order-lifecycle-api` | Новых миграций нет |
| VK launch freshness | `claims-api`, `master-memo-api`, `order-lifecycle-api`, `drive-archive-api` | BOS token format/TTL не изменяются |
| Частичный импорт | `_shared/lemana-api.ts`, включённый в `mini-app-api` | Существующая create-only RPC сохраняется |
| Клиентский pending | Только отдельная portal-ветка, `client-portal/server/api.cjs` | Не включать в выпуск сотрудников; отдельный release |
| package/CI/документы/сборщик | Разработка и проверка | Не требуют перезапуска production |

Эти новые изменения не требуют изменения финансовых правил, пересчёта выплат или массового ремонта данных. Но базовая ветка уже содержит более ранние миграции/функции, применение которых к RU неизвестно. Их нельзя автоматически применить вместе с аудитом.

## 1. Получить исходную точку без изменений

Подготовленный сборщик: `scripts/audit-production-readonly.py`. Запускать из отдельного проверенного checkout, а не из рабочего каталога приложения. Скрипт выводит git HEAD/число изменений, доступные `bos-*` images/state/health, хеши frontend/source/eszip и сопоставление manifest. Не выводит env, строки клиентов, тела конфигов/логов, ключи. Не перезапускает сервисы и не пишет БД. Docker/права могут быть недоступны; в этом случае выдаёт структурированный unavailable.

По умолчанию `--repo .`: Git-блок относится к диагностическому checkout, из которого запускается скрипт, **не доказывает commit установленного приложения**. После определения реального server checkout передать его путь через `--repo`; если установленный артефакт не содержит Git, явно зафиксировать это и сопоставлять его по manifest/хешам. Docker-хеши рассматриваются отдельно от Git-блока.

Короткая команда запуска (44 символа):

```sh
python3 scripts/audit-production-readonly.py
```

БД по умолчанию **не читается**. Для метаданных требуется явно выбрать актуальные container/database; исторические `bos_restore_check` и `bos-release-to2wblxf-db` не являются автоматически правильными. После идентификации подготовить отдельную короткую команду с проверенными значениями. SQL ограничен каталогами/числовыми версиями миграций, READ ONLY и timeout. Скрипт сам по себе не устанавливает соответствие source→bundle или пригодность backup.

Сопоставить также отсутствующий `vk-session-api`, RU router, активные CORS/origins, версии самого Edge runtime и внешних модулей. Для триггеров нужны определения/хеши после безопасного просмотра, не бизнес-строки. Полные конфиги/секреты в чат не передавать.

## 2. Подготовить проверенный пакет

1. Зафиксировать текущие runtime-файлы и digest, серверные доработки и маршрутизацию. Выделить только новые изменения аудита поверх установленной базы. Сохранить уже выпущенные дату поступления, телефон, отчёты, файлы, финансы и прайс.
2. Подготовить отдельный release-каталог, manifest с commit/hash/образами и неизменяемый артефакт. Сборка из исходников должна совпадать с ожидаемым набором. Не запускать `npm build` в live.
3. Подтвердить пригодную копию затрагиваемого кода/конфигурации и независимую восстановимую копию данных. Обычный откат кода не должен требовать отката всей БД.
4. На копии использовать собственные БД/Storage/keys/origin и синтетические данные. Блокировать реальные push, Avito, Hands, Google, рабочие webhook/cron. Проверить исходящие адреса до старта.
5. Воспроизвести исходные дефекты и отрицательные роли на настоящем установленном runtime, а не только VM. Проверить create→contact→report→review→finance, lost response, повтор, reload/new session и файлы. Если runtime отличается, адаптировать минимальный patch и повторить проверку.
6. Полный CI последнего SHA должен быть зелёным. Новый workflow проверяет stacked PR. GitHub approval/merge не равны отдельному разрешению владельца на production.

## 3. Применение — только после отдельной команды владельца

После сверки подготовить installer с `stage`, `apply`, `rollback`, точными before/after hashes, блокировкой неизвестного состояния и тестом восстановления при прерывании. Нельзя сейчас честно заполнить актуальные имена контейнеров/пути/хеши, поэтому исполняющий production-installer не выдуман. Это конкретный блокер, а не предложение выполнить слепую установку.

Для оператора все команды должны быть ≤60 символов, каждая отдельно, только ближайший шаг. Длинные действия находятся в проверенном файле. Не использовать `curl | sh`, большие heredoc и копирование SQL в консоль.

После отдельного разрешения: сохранить current manifest, stage, проверить stage, атомарно переключить только согласованные сервисы/артефакты, выполнить smoke. Изменение DNS/портов/proxy не входит в этот набор. Backend и frontend version учитывать раздельно: unchanged frontend BUILD_ID не означает, что backend не обновлён.

## 4. Проверка результата

Проверить точные digest и build ID, вход/выход, роль мастера и менеджера, сохранение даты/контакта, пустой файл → понятный отказ, полноценный отчёт → pending после повторного входа, возврат с причиной, принятие и просмотр фото/акта. Сравнить суммы и XLSX одного мастера до/после без пересчёта истории. Импорт retry проверять на выделенных тестовых данных копии; рабочие заявки не создавать ради smoke без согласованного сценария.

Проверить ошибки сервисов, не раскрывая токены/клиентские тела. Реальные устройства и выделенный push-получатель требуются отдельно; наличие 2xx от провайдера недостаточно. Отметить результат каждого пункта, а не только «контейнер running».

## 5. Откат

- Триггеры отката: новый 5xx/ошибка входа, отчёт не сохраняется, ошибка ролей/начислений, несовпадение digest, потеря файловой доступности.
- Сначала остановить продвижение релиза; сохранить обезличенные ошибки, текущие digest и время. Вернуть ровно предшествующий backend/артефакт и исходную конфигурацию через проверенный installer. Не выполнять git reset в live.
- Новых схемных миграций аудит не добавляет, поэтому обычный rollback не должен изменять бизнес-таблицы. Более ранние миграции базовой ветки рассматриваются отдельно по их фактическому применению.
- Не восстанавливать старый полный дамп поверх новых заявок как обычный откат. Если повреждены данные, нужен отдельный preview/diff, идемпотентный ремонт и сохранение состояния каждой затронутой строки; такой ремонт сейчас не запускался.
- Повторить smoke и сверку денежных итогов. Возврат старой auth-версии возобновит прежний риск replay, это временная мера, требующая последующей исправленной поставки.

Пакет считается готовым к публикации только после сопоставления live, прохождения stage на соответствующем runtime, проверки rollback и зелёного CI точного SHA. Текущий результат готов к ревью исходников; эти production-предусловия ещё не закрыты.
