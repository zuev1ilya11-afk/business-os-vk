## 2. Вход: установленное и неизвестное

Последние материалы показывают предыдущие сбои локали PostgreSQL и запуска Edge (`RUNTIME_EVENT_LOOP_EXITED`). Они не доказывают причину нынешнего «сервер не отвечает» после пакета v6. Первый неуспешный запрос именно пользовательской попытки, его время и соответствующая запись сервиса пока отсутствуют.

Фактическая цепочка пароля по коду: frontend → локальный portal/proxy → Caddy `:18080` → Edge `:9000` → `password-session-api` → PostgREST RPC `bos_consume_login_attempt`/`bos_verify_staff_credentials` → `business_staff`. Это собственная HMAC-сессия; GoTrue `/auth/v1/token` не является штатным маршрутом этого входа.

Уже существующий локальный пакет создаёт новый том от восстановленного baseline, свежие ключи, сеть `none`/общий loopback без опубликованных Docker-портов, отдельный профиль браузера; workers и внешние push/Hands/Avito/VK/GAS/Drive заблокированы. Эти свойства проверены по коду/контрактам. В новом live JSON подтверждены network-none, общий loopback, собственный том, отсутствие внешних mounts и host ports на момент проверки. Переключение роли требует исходной owner session и серверной записи сотрудника, но его fixture-тест не доказывает реальные права четырёх аккаунтов.

Подтверждён отдельный дефект диагностического дополнения: ответ с текстом «неверный логин» мог считаться корректным без проверки HTTP-статуса и отсутствия выданной сессии. Исправлены строгие требования к 401/`ok=false`/отсутствию токена; отчёт v2 содержит метод, фиксированный локальный путь, время UTC, длительность и первый неуспешный диагностический запрос. Это исправление диагностики, **не исправление установленной причины входа**. Секреты и сырые журналы не выводятся.

В JSON `storage_relationships=NOT_VERIFIED`, `database_storage_consistency=NOT_PROVEN`, `storage_extended_attributes=NOT_CAPTURED`, `application=NOT_RUN`, `disaster_recovery_ready=false`. Поздний app JSON подтвердил clone counts, но остановился на Edge. Приватный backup не передавался; локально Docker CLI/daemon отсутствуют. Нельзя объявлять recovery полностью готовым или повторять большой restore без нужды.

Откат кандидата:

1. UI/диагностика: вернуть предыдущие точные артефакты baseline; кодовый откат не требует восстановления БД. Новый pyz — только дополнение диагностики, не заменяет работающий app package.
2. Новая миграция additive, не обновляет старые orders/деньги. Предыдущий код может работать с новой архивной таблицей. Сохранить таблицу и триггер при обычном откате frontend, чтобы не терять новые версии.
3. При доказанном отказе архивного триггера сначала остановить проверку/сохранить доказательства и исправить вперёд; если необходимо временно отключить только этот триггер, сохранить архив и явно учесть, что новые удаления отчётов больше не защищены. Автоматический down/drop не поставляется.
4. Старый dump поверх текущих заявок и денег не восстанавливать как способ отмены кода. Не удалять все Docker volumes. Совместимость/откат на настоящей Windows-копии ещё не испытаны.
