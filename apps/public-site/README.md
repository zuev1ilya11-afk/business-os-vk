# Публичный сайт Business OS

Независимый Next.js / React / TypeScript SSR-проект. Общий API — из PR #303, общие заявки сотрудников и клиентский PWA. Production автоматически не публикуется.

## Изолированный запуск

Из корня репозитория установить зафиксированные зависимости `npm ci`, `npm ci --prefix client-portal`, `npm ci --prefix apps/public-site`. Нужен Node.js 24.

`npm run dev` запускает сайт на `http://127.0.0.1:4173/`, клиентский кабинет на `/client/`, сотрудников на `/staff/`. База PGlite и файлы создаются только в `.public-site-stage/`. Настоящие сервисы доставки, SMS и production БД отсутствуют. `npm run dev:client` сохраняет прежний самостоятельный запуск кабинета.

Тестовые SMS находятся в закрытом `.public-site-stage/private/otp/`. Пароли синтетических сотрудников — в `.public-site-stage/private/access.json`. Не открывать эти файлы через HTTP, не коммитить, не прикладывать к отчётам. Playwright читает тестовые значения внутри процесса без вывода.

На preview-платформе используется её managed launcher; URL `http://terminal.local:4173/` действует внутри сессии. Это не staging на российском сервере и не постоянный публичный адрес.

## Проверки

| Команда из корня | Назначение |
|---|---|
| `npm run test:website` | Каталог, права, интеграция, откат и восстановление |
| `npm run test:client` | Регрессии существующего клиентского API |
| `npm run test:server` | Регрессии сотрудников и финансов |
| `npm --prefix apps/public-site run build` | TypeScript и production SSR-сборка |
| `npm run build:check` | Общий BUILD_ID и сборочные файлы сотрудников |

Для браузерных тестов в `apps/public-site`: `npx playwright test --config playwright.config.cjs`. Предварительно собрать сайт и установить Chromium командой `npx playwright install chromium` из корня. Тестовый HTTP-порт — 4191. Порт 4190 не использовать: он запрещён стандартным fetch.

Полный прежний UI-набор запускается только через `scripts/test-ui-offline.sh`: он изолирует сеть и не допускает обращения к production. В локальной среде sudo/unshare недоступны; обходить изоляцию нельзя. Набор исполняется в CI на Ubuntu 24.04 без деплоя и production secrets. Фактический результат записан в `docs/public-site/report.md`.

## Docker и nginx

`Dockerfile` содержит только публичный Next runtime. `Dockerfile.staging` содержит интегрированный синтетический стенд. `compose.staging.yml` — отдельный проект и отдельный volume, порт привязан к 127.0.0.1:4185, а не ко всем интерфейсам. Не добавлять его автоматически в существующий production Compose.

Из этой директории команда проверки: `docker compose -f compose.staging.yml config --quiet`. Сборка/запуск: `docker compose -f compose.staging.yml up -d --build`. Локально Docker отсутствует. В CI успешно выполнены сборка и запуск синтетического контейнера, HTTP smoke, отдельная production-сборка и nginx syntax check; результаты и ссылка на прогон — в `docs/public-site/report.md`.

`ops/nginx.conf.example` — шаблон отдельного виртуального хоста. До применения проверить свободные порты и действующую конфигурацию, добавить согласованный HTTPS-вход. Он направляет `/client/` к существующему PWA, `/client-api/` — к существующему API, блокирует публичный `/client-api/staff/`. Сотрудники продолжают работать на своём техническом origin. Адреса 4173, 4181, 4185 и 8086 — предложенные, на RU они не измерены.

## Настройки и выпуск

### Закрытый просмотр на RU через существующий Caddy

На сервере 06.11.2026 подтверждены Caddy 2.11.7 с host network, admin
`127.0.0.1:12019`, каталог `/etc/caddy` как directory bind mount, отдельный
staging на `127.0.0.1:4185` и DNS `site.homemaster.qd.je → 139.100.237.167`.
Рабочий домен сотрудников — `homemaster.qd.je`, его DNS использует второй
адрес того же сервера `136.234.17.113`.

Для **нового сайта** установщик явно использует Let's Encrypt ACME.
Существующие issuer/policy сотрудников сохраняются. 07.11 Let's Encrypt
вернул общий лимит для `qd.je`; эксперимент с ZeroSSL остановлен после сбоя
регистрации и проверки [ограничений работы из РФ](https://help.zerossl.com/hc/en-us/articles/17938565588637-Usage-Restrictions).
До изменений установщик читает последние события Caddy для этого hostname
и останавливается, если известный retry-after ещё не наступил. При новом
отказе по квоте ожидание сразу прекращается с откатом. Указанное CA время
выводится по Москве; это время следующей попытки, а не гарантия доступной квоты.
Email можно задать через `WEBSITE_ACME_EMAIL`; иначе используется единственный
явный ACME email прежней конфигурации, если он есть. Для Let's Encrypt email
не обязателен, отсутствие/неоднозначность контакта не блокирует запуск.
Реальный email в репозиторий не входит. Таймаут остальных HTTPS-проверок
ограничен пятью минутами и теперь включает последнюю ошибку CA этого сайта
без email и URL-параметров; полный журнал сотрудников не печатается.
Проверка CA/SNI остаётся строгой. Пересборка runtime-образа не требуется.

Когда общий лимит зоны мешает выпуску, `python3 ops/publish.py --apply --ip`
публикует тот же закрытый стенд на `https://139.100.237.167:8443`.
Перед изменениями проверяются свободные TCP/UDP 8443, действующий доверенный
IP-сертификат на 443 (до истечения больше часа) и существующая политика
Let's Encrypt `shortlived`. Сертификат и приватный ключ не копируются:
новый listener использует общий кеш Caddy и прежнее автоматическое продление.
Нативный JSON должен сохранить все существующие серверы и TLS-настройки.
Новый listener принимает HTTPS на 8443, а маршрут отвечает только на указанный
IP в Host; остальные имена не получают содержимое сайта. Docker по-прежнему слушает только
4185 на loopback. `.env` получает точный HTTPS origin
с портом. Проверяются одинаковый сертификат на 443/8443, пароль, страницы,
API, private-path 404, прежние IP-страницы и HTTP-перенаправления. Проверка HTTPS
занимает не более 45 секунд; отказ возвращает прежние настройки.
DNS/выдача нового сертификата и изменение firewall для этого режима не выполняются.
Доступ к TCP 8443 извне должен разрешаться сетевыми правилами сервера/провайдера;
это проверяется из браузера после успешных локальных проверок.

Если установленный IP-preview недоступен через `139.100.237.167`, но внешний
клиент уже подтвердил доверенный HTTPS на `136.234.17.113:8443`, запустить
`python3 ops/publish.py --apply --switch-ip`. Режим переносит только ранее
установленный preview на второй адрес: сохраняет пароль и его хеш, меняет
Host/SNI matcher отдельного listener, оба staging origin и URL в закрытом
access-файле. Весь остальной Caddyfile, серверы, сертификаты и их продление
должны остаться прежними. Проверки подключаются к назначенному локально второму
IP, чтобы при отсутствии IP-SNI Caddy выбрал его существующий сертификат;
глобальный `default_sni` не меняется. Создаётся закрытая резервная копия,
перезапускается только staging без сборки; при ошибке выполняется откат.

Подготовленный `ops/publish.py --apply` запускается из свежего checkout на
этом сервере от root. После изменения runtime-кода сначала собрать и запустить
обновлённый staging командой `docker compose -f compose.staging.yml up -d --build --wait`.
Сначала установщик проверяет активную конфигурацию Caddy против
Caddyfile, локальный HTTPS рабочего домена, DNS, состояние staging, отдельный
volume и loopback port. Затем валидирует новый Caddyfile, сохраняет backup в
`/var/backups/bos-public-site/`, устанавливает origin сайта через игнорируемый
`.env`, пересоздаёт **только staging** из прежнего образа и выполняет graceful
reload Caddy. Данные/образ/статика/БД сотрудников не изменяются.

Для сравнения после reload используется JSON, полученный из конечного пути
`/etc/caddy/Caddyfile`; именно этот JSON передаётся Caddy через stdin. Это
сохраняет неявный список `file_server.hide`, зависящий от имени конфигурационного
файла. JSON временного кандидата не используется как ожидаемая рабочая конфигурация.
При откате восстанавливаются прежний файл и точный прежний активный JSON.
Ожидаемые и фактические JSON при несовпадении остаются только в закрытом backup.

HTTPS-адрес синтетического стенда требует отдельного точного opt-in
`WEBSITE_STAGING_HTTPS_ORIGIN`, совпадающего с `WEBSITE_STAGING_ORIGIN`.
Установщик задаёт оба значения в `.env`. API разрешает этот режим только для
изолированного website staging с тестовой доставкой; production по-прежнему
отклоняет test transport. Без opt-in удалённый адрес отклоняется. Проверка
входящего Origin остаётся точной, session cookie получает Secure.

Весь новый хост закрыт Basic Auth; пароль генерируется на сервере и сохраняется
только после успешных проверок в `/root/bos-site-access.txt` с правами 0600.
Логин — `preview`. Пароль не выводится в журнал, не передаётся в argv и не
пересылается приложению. Robots/noindex включены. Проверяются TLS с системным
trust store, закрытый вход, страницы, API health, private-path 404 и неизменность
ответа главной сотрудников. При ошибке после изменений установщик возвращает
старый Caddyfile/origin и перезапускает только staging. Если обнаружена чужая
параллельная правка, её не перезаписывает: сохраняет backup и останавливается.
Повторный запуск при уже существующем сайте/файле доступа остановится без
дублирования блока и смены пароля.

Это **синтетический стенд для владельца**, а не приём настоящих клиентских
заявок: SMS тестовые, БД отдельная. Успех установщика доказывает локальные
проверки на RU; доступ из браузера пользователя проверяется отдельно.

Проверки установщика: `python3 -m unittest discover -s apps/public-site/tests
-p 'test_publish.py' -v`. CI дополнительно запускает настоящий Caddy 2.11.7
на одноразовом runner: синтаксис с наблюдавшимися IP/ACME-настройками, закрытие
всех маршрутов, отсутствие gateway-пароля в upstream, noindex, сохранение
соседнего хоста, graceful reload и возврат предыдущей конфигурации. Эти
проверки не обращаются к RU. Сам установщик выполняется только вручную.
Дополнительно CI перезапускает настоящий собранный контейнер с HTTPS origin
на сохранённом синтетическом volume, проверяет страницы, правильный/чужой
Origin формы, тестовый OTP-вход, Secure cookie и закрытый private path.
При ошибке Docker установщик сохраняет диагностические журналы в закрытом
каталоге backup перед откатом; содержимое в консоль не выводится.

### Production

`.env.example` не содержит секретов. `NEXT_PUBLIC_*` являются открытыми сборочными параметрами; домен/контакты нужно передать при сборке, в Docker — соответствующими build args. `NEXT_PUBLIC_SITE_URL` также нужен runtime для robots/sitemap. Это должны быть согласованные одинаковые значения. В staging пустой домен отключает canonical и sitemap URLs, robots запрещает индексацию.

`WEBSITE_ENV=production` запускает только публичный сервер, без синтетической БД и доступа сотрудников. Нужны HTTPS `NEXT_PUBLIC_SITE_URL` и контролируемый `WEBSITE_INTERNAL_API_ORIGIN`. `/healthz` проверяет живой процесс сайта; готовность БД отдельно проверяет `/client-api/health`.

В API флаг `CLIENT_WEBSITE_ENABLED` по умолчанию выключен. Включение требует website-схему версии 1 и все клиентские миграции до версии 5. `CLIENT_WEBSITE_ORIGINS` — точные HTTPS origins; без wildcard. Предпочтительная первая схема — один origin сайта и `/client/`, чтобы существующая host-only cookie безопасно работала без второго OTP. Отдельный поддомен кабинета потребует отдельно спроектированного и проверенного SSO.

Числовые цены берутся только из `service-catalog.js`; публикация подтверждает fingerprint позиции. Изменение исходной цены автоматически переводит показ в «После уточнения». Неподтверждённые коэффициенты не придумываются. Начальные публичные метаданные автоматически загружаются только в изолированном стенде; публикации для настоящей БД требуют проверки владельцем.

Юридические документы читаются из реализации PR #303 без изменения текста/версий. Для публичного запуска нужны утверждённые документы, реквизиты, контакты, тарифы и отдельное разрешение на production/SMS/DNS/secrets. Реальный читатель актов из RU Storage пока не подключён; защищённый маршрут проверен на изолированном хранилище. Push не подключён; новые B2B-лиды видны в очереди и счётчике сотрудников (обновление раз в минуту).

## Откат

Первый, минимальный откат: отключить входящий публичный сайт и website feature, вернуть предыдущий образ/статику; общие заявки и файлы сохраняются. Таблицы можно оставить — схема добавочная.

Если требуется откат схемы: сначала остановить все website-записи и API с website feature, проверить резервную копию, затем отдельно согласованно применить `ops/rollback.sql`. Он переносит website-таблицы в закрытую архивную схему и скрывает связанные публикации, сохраняя их предыдущие флаги. Общие orders, финансовые снимки и файлы не удаляются. Добавочная колонка публичного телефона остаётся, старый API её не читает.

`ops/restore-schema.sql` возвращает архивные таблицы и флаги публикации. Скрипты рассчитаны на однократный контролируемый цикл; существующая архивная схема блокирует повторный rollback. Не применять миграцию заново поверх архива. Восстановление проверено на закрытой копии PGlite и private-файлов; настоящая PostgreSQL требует отдельной проверки pg_dump/pg_restore и объектного хранилища.
